# 从进程级模拟到真机测试的联调计划

## 1. 文档目的

本文档用于定义当前仓库“寻找物体”与语音链路的联调推进路线。  
当前主线不再是“server / glass / phone 全部本机模拟”或容器化联调，而是：

- `server`：本机 Python 进程
- `glass`：本机 Python 进程，可接本机摄像头、麦克风、喇叭
- `phone`：iPhone 真机运行 Flutter App
- `test support`：本机 Web 测试支持服务

## 2. 当前主线阶段

### 阶段 A：标准测试数据与离线验证

目标：

- 保留固定输入样例，约束任务协议与结果语义
- 用图片、视频、文本、音频样例做可回放验证

当前保留的测试数据目录：

- `testdata/voice/`
- `testdata/find_object/`
- `testdata/imu/`

### 阶段 B：本机双进程 + iPhone 真机联调

目标：

- 本机启动 `server` 与 `glass`
- iPhone 真机启动 `clients/phone_flutter`
- 通过测试支持服务统一注入文本、图片、视频和语音动作

当前入口：

```bash
uv run python scripts/run_local_test_support_service.py
```

真机操作参考：

- [iPhone真机联调操作清单.md](/Users/elio/dev/llm-project/OpenAIglasses_for_Navigation/docs/total/test-stages/iPhone真机联调操作清单.md)

### 阶段 C：真实传感器替换

目标：

- `glass` 使用本机真实摄像头、麦克风、喇叭
- `phone` 使用 iPhone 真机网络环境与本地任务服务
- 保持服务器与测试支持服务不变

### 阶段 D：专项真机回归

目标：

- 针对“找物”“对讲模式”“实时对话”分别形成稳定回归步骤
- 确认日志、状态页、手机 UI 三方观测一致

## 3. 已退役方案

以下方案都已经退役，不再作为维护中的主链路：

- 全部三端本机三进程模拟
- 已退役的容器与总线历史方案
- 依赖 Python 手机模拟运行时的 demo / runner

保留这些历史文档的唯一目的，是提醒后续不要再回到已经退役的测试形态。

## 4. 当前推荐顺序

1. 准备标准测试数据
2. 启动本机测试支持服务
3. 在 iPhone 真机上运行 Flutter App
4. 先打通注册 / 心跳 / prepare-peer-link
5. 再验证找物图片与视频链路
6. 最后验证对讲模式与实时对话模式

## 5. 当前结论

当前仓库的联调基线已经固定为：

- 本机 `server`
- 本机 `glass`
- iPhone 真机 `phone`

任何后续测试、文档和代码都应以这条主线为准，不再继续维护旧的三进程 / 容器模拟方案。
