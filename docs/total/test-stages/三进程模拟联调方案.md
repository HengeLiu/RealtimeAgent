# 三进程模拟联调方案

## 1. 文档目的

本文档用于说明如何基于当前 `nextgen/` 代码，以“三个独立运行时”的方式模拟眼镜、手机、服务器的协作过程。

本文档对应 [从进程级模拟到真机测试的联调计划.md](./从进程级模拟到真机测试的联调计划.md) 中的“阶段一：进程级模拟”，重点关注：

- 当前仓库中已经落地了哪些代码
- 如何使用标准测试数据驱动模拟联调
- 这一阶段的结果如何约束后续真实多进程联调和真机联调

## 2. 当前已落地实现

当前仓库已经具备以下基础能力：

- `testdata/`：标准测试数据目录
- `nextgen/integration/smoke/testdata_loader.py`：标准测试数据加载器
- `nextgen/integration/smoke/process_simulator.py`：寻找物体三进程模拟器
- `nextgen/integration/find_object/runner.py`：寻找物体黄金链路集成运行器

当前阶段仍然是 Python 参考实现，但已经可以明确模拟三类运行体：

- 眼镜运行时
- 手机运行时
- 服务器运行时

## 3. 标准测试数据位置

当前测试数据按以下目录组织：

- `testdata/voice/voice_cases.json`
- `testdata/find_object/find_object_cases.json`
- `testdata/imu/imu_cases.json`

这些数据具备以下作用：

- `voice_cases.json`：约束语音触发和状态查询输入
- `find_object_cases.json`：约束找物联调场景输入和预期输出
- `imu_cases.json`：约束姿态类数据回放格式

## 4. 三进程模拟的运行方式

当前三进程模拟的最小运行入口是 `ThreeProcessFindObjectSimulator`。

它的主要职责包括：

- 从标准测试数据中读取单个 `case_id`
- 调用寻找物体黄金链路运行器
- 返回包含三端描述、预期值和实际结果的结构化报告

当前阶段它仍然运行在同一 Python 进程中，但已经显式保留了三端边界：

- `glass-runtime`
- `phone-runtime`
- `server-runtime`

后续真实多进程拆分或真机替换时，应继续保留这三端边界和当前输入输出格式。

## 5. 推荐使用方式

当前推荐以标准 case 为单位执行模拟联调。

推荐优先使用以下三个 case：

1. `find_object_phone_center_001`
2. `find_object_wallet_missing_001`
3. `find_object_phone_grasp_001`

它们分别覆盖：

- 正常发现目标并完成任务
- 未找到目标时继续扫描
- 手已接触目标时给出稳定引导

## 6. 当前阶段的约束意义

本方案的意义不是替代真机联调，而是提供后续实现的行为基线。

后续无论手机端和眼镜端如何迁移到其他语言和真实硬件，都应满足当前三类约束：

- 同样的 `case_id` 能映射到同样的输入语义
- 同样的任务生命周期能在日志中复现
- 同样的找物场景能得到同方向的引导结果

## 7. 当前未完成的内容

当前三进程模拟仍有以下内容未实现：

- 真正的操作系统级三进程启动脚本
- 真实音频文件驱动的语音事件形成
- 真实图片或视频驱动的帧流回放
- 真正的网络传输层隔离

这些内容属于后续“I/O 数据模拟增强”“混合联调”和真机联调阶段。
