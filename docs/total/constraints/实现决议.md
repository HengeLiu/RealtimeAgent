# 实现决议

## 1. 文档目的

本文档用于固化当前已经达成一致的实现决议，作为后续代码实现的强约束。  
除非后续明确修订本文档，否则实现应默认以本文为准。

---

## 2. 总体决议

### 2.1 新实现与旧实现隔离

- 新架构和新实现放入一个新的顶层目录中
- 老文件先保留，不删除，不在第一阶段强制迁移
- 第一阶段禁止在旧代码上继续堆叠新架构逻辑

### 2.2 新实现目录名称

- 暂定新实现目录为 `nextgen/`
- 后续所有新的三端运行时代码、共享模型、协议定义、抽象接口，优先放入 `nextgen/`

### 2.3 三端职责边界

- 眼镜端负责感知采集、轻量事件化、执行输出、设备控制
- 手机端负责高频视觉任务、本地持续任务组件执行
- 服务器端负责智能体、任务编排、状态中心、日志记录、Skills 与 MCP 调用

### 2.4 语音输入链路

所有语音输入必须遵循以下链路：

`sensor_hub -> event_detector.vad -> event_detector -> glass_gateway -> server_gateway`

禁止：

- 眼镜接入层直接把裸语音语义化后上送服务器
- 任务绕过 `sensor_hub` 直接控制麦克风

### 2.5 采集请求原则

- 所有任务都可以提出采集请求
- 任务不能直接操作采集器
- 所有采集请求必须进入 `sensor_hub` 仲裁
- 允许多个任务竞争同一个采集器，由 `sensor_hub` 统一复用、降级、延迟或拒绝

### 2.6 执行输出原则

- 所有播报、提示音、震动必须先进入 `executor_bus`
- `device_control` 只负责执行器，不负责采集器
- 引导建议可以由手机直接发给眼镜，但眼镜仍必须通过 `executor_bus` 执行

### 2.7 控制面与数据面

- 控制面默认经服务器中转
- 数据面允许 `relay` 和 `peer`
- 第一阶段先定义两种模式，但实现上可先只做稳定可用的一种

### 2.8 Skills 与 MCP 分离

- `skills_registry` 与 `mcp_registry` 分开维护
- 不强行统一 Skills 与 MCP 的输入输出格式
- 智能体调用时可以统一抽象为工具，但实现层保持分离

### 2.9 智能体中心职责边界

- `agent_center` 负责理解意图、调用工具、回答任务状态问题
- `agent_center` 不主动追问已启动任务
- 后台任务状态维护由 `background_task_center` 负责

### 2.10 第一条黄金链路

- 第一条完整打通的功能固定为“寻找物体”
- 后续其他功能均以“寻找物体”链路为样板扩展

---

## 3. 当前明确不做的事情

在进入代码实现前，以下内容不作为第一阶段必做项：

- 一次性把所有旧代码迁入新结构
- 一次性打通所有功能
- 一开始就做完整的设备直连优化
- 一开始就实现所有业务逻辑细节
- 一开始就做完整的前端管理页面
