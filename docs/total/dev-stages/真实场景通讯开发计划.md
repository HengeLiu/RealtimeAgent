## 2. 与原有阶段的关系

前四个阶段已经完成了以下基础能力：

- `nextgen/` 三端与共享层代码骨架已建立
- 旧代码中的关键能力已迁移到 `nextgen/`

从真实场景通讯方案来看，当前工作需要重新聚焦为以下 3 个方向：

1. 控制面 HTTP
2. 任务级 WebSocket 数据面
3. 异常断链后的恢复机制

### 3.2 还没有实现的部分

当前仍缺少：

- 眼镜与手机之间真正的任务级 WebSocket 数据面
- 眼镜通过数据面向手机发送“找物单帧分析输入”或等价帧消息
- 手机通过数据面直接向眼镜返回引导建议
- 眼镜执行引导建议后向服务器回传执行状态

- 眼镜断链后自动向服务器上报
- 服务器在断链后执行一次恢复或给出失败结论

## 4. 重新拆分后的开发阶段

### 阶段 A：控制面补完

目标：

- 在现有 HTTP 控制面的基础上补足真实任务状态接口
- 让服务器不只知道“链路状态”，也知道“任务运行状态”
- 为后续数据面和恢复流程提供稳定控制入口

本阶段应完成：

- `POST /tasks/{session_id}/state`
- `POST /tasks/{session_id}/guidance-executed`
- `POST /tasks/{session_id}/peer-link/broken`
- `POST /tasks/{session_id}/peer-link/recover`

通过标准：

- 服务器可完整记录任务状态、执行状态、断链状态

---

### 阶段 B：任务级 WebSocket 数据面

目标：

- 在手机侧启动任务级 WebSocket 监听入口
- 眼镜按服务器下发的任务参数主动连接手机
- 眼镜与手机通过同一条任务级长连接交换找物所需消息

本阶段应完成：

- 手机端任务级 WebSocket 服务端
- 眼镜端任务级 WebSocket 客户端
- 找物单帧分析消息定义
- 手机返回引导建议消息定义
- 任务结束后的连接释放

通过标准：

- 一次找物任务中，眼镜可通过 WebSocket 给手机发分析输入
- 手机可通过 WebSocket 直接给眼镜回引导建议

---

### 阶段 C：找物真实通讯闭环

目标：

- 让“寻找物体”真正跑在“本机 server + 本机 glass + iPhone 真机 phone”的 HTTP 控制面 + WebSocket 数据面组合上
- 让服务器只收任务状态，不承接完整引导文本

本阶段应完成：

- 眼镜向手机发送找物分析输入
- 手机本地执行 `FindObjectTask`
- 手机直接把引导建议发回眼镜
- 眼镜通过 `executor_bus` 执行引导
- 手机向服务器汇报任务状态
- 眼镜向服务器汇报执行状态

通过标准：

- 一条真实联调链路能跑通“创建任务 -> 建链 -> 发送分析输入 -> 收到引导 -> 执行 -> 收尾”

---

### 阶段 D：异常断链与恢复

目标：

- 支持眼镜发现连接失败或异常中断后上报服务器
- 服务器负责协调一次重建连接
- 若恢复失败，服务器能给出清晰失败状态

本阶段应完成：

- 眼镜侧断链上报
- 服务器侧恢复接口
- 服务器侧一次重试逻辑
- 恢复失败后的状态落库与页面可见

通过标准：

- 至少一条测试覆盖“断链 -> 上报 -> 恢复成功”或“断链 -> 恢复失败”

---

## 5. 开发顺序

建议严格按以下顺序推进：

1. 先补阶段 A 的控制面接口
2. 再补阶段 B 的 WebSocket 数据面
3. 然后打通阶段 C 的找物完整通讯闭环
4. 最后实现阶段 D 的断链恢复

原因：

- 没有任务状态接口，数据面跑通后也无法在服务器上形成可观测状态
- 没有数据面，找物链路仍然只是控制面参考实现
- 没有恢复逻辑，真实场景鲁棒性仍不足
