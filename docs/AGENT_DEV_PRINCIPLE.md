# 代码编写注释原则

1. 类都应该有注释，说明其主要功能、主要方法、主要属性。
2. 函数都应该有详细的注释，包括函数功能、主要逻辑、参数、返回值和异常情况。
3. 注释应该采用中文，避免使用专业术语。

# 文档编写原则

1. 每一个文件目录下都应该有一个README.md文件，说明该目录的主要功能，以及目录下的每个文件的主要功能。
2. 技术设计文档需要持续与当前真实代码状态保持一致，已经落地的功能、未实现的功能、最小实现取舍都要明确写出。

# 测试代码编写原则

所有需求都必须按照四层测试法编写测试案例：

1. 场景测试：为确保能够交付完整的产品能力，根据 PRD 文档里描述的各种可能得场景组合，构造五个以上的用户场景，这些场景必须至少覆盖PRD中已经提到的场景，最好能在包含一些其他可能出现的场景，每个场景应该是以上几个功能点的组合，不能只涉及到一个功能点，不可以使用mock方法；
2. 集成测试：为确保需求中每个功能点都实现的测试过程，集成测试应当按照根据需求PRD拆分出的功能点展开测试，每一个功能点至少编写三个不同的测试案例，不可以使用mock方法；
3. 接口测试：为了确保团队合作正常开展，是API层面的测试，例如前后端联调前，应该对约定好的接口功能、输入输出数据格式进行测试，可以使用mock完成；
4. 单元测试：为了确保每个功能点的实现质量，是最小测试单元，主要测试原子性的核心方法、逻辑是否复核预期，可以使用mock完成；

一般会先编写集成测试和功能测试代码，所以尚未实现的功能点可以先使用空方法占位，等功能实现后再调整测试代码到真实实现。
