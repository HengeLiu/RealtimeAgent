# 统一控制消息信封设计

## 1. 目标

本设计解决的是三端协作中的“控制消息不统一”问题。

新架构下，眼镜、手机、服务器不应再依赖旧项目那种“某个 WebSocket 路径 + 某段裸文本命令 + 某个隐式全局状态”的协作方式。所有控制类消息都应包裹在统一信封中，使以下模块可以用同一套方式处理消息：

- `glass-api`
- `phone-api`
- `server-api`
- `sensor-hub`
- `actuator-hub`
- `agent-core`
- `backend-task-core`

## 2. 设计原则

1. 统一的是控制语义，不强制统一底层传输。
2. 所有控制类消息统一使用一种 `ControlMessage`。
3. `Stream` 可以继续沿用旧项目的独立流式传输方式，但必须由 `ControlMessage` 建立、控制和结束。
4. 所有消息必须可追踪、可去重、可关联任务。
5. 同一设计同时兼容眼镜、手机、服务器与后续 Tool/MCP 调用。
6. 旧项目里已经验证过的媒体传输方式可以保留，例如音频上行流、视频帧流、音频下行流；变化的是这些通道上的业务控制语义。
7. 统一信封不等于统一状态中心，状态只在少数真正需要的主体内部维护。

## 3. 控制消息模型

### 3.1 ControlMessage

本设计采用一种统一控制消息：

- 统一 envelope
- 统一路由
- 统一追踪
- 统一错误处理

不同消息意图通过 `semantic` 字段体现。

需要强调：

- 对外协议文档只保留 `request`、`notify` 两种语义标签
- 事件通知和状态上报都统一归入 `notify`
- 这些标签只是帮助理解消息意图，不代表多套并行协议

### 3.2 semantic 语义分类

建议 `semantic` 取值如下：

- `request`
  - 表示“请求对方执行一个动作”
- `notify`
  - 表示“某个事实已经发生”或“当前状态快照/状态变化报告”

示例：

- `device.register`
- `voice.session.open`
- `actuator.audio.play`
- `peer_link.prepare`
- `device.registered`
- `sensor.audio.segment.started`
- `sensor.audio.segment.finished`
- `peer_link.ready`
- `device.state.report`
- `task.state.changed`
- `actuator.audio.state`

### 3.3 Stream

表示“持续数据流”。

示例：

- 音频块
- 图片帧
- 视频流
- IMU 高频数据

说明：

- `Stream` 不要求直接套 JSON envelope。
- 但每条流必须先通过一条 `ControlMessage` 建立上下文，再通过 `stream_id` 和元数据完成关联。
- 这意味着旧项目里类似 `/ws_audio`、`/ws/camera`、`/stream.wav` 的物理通道可以保留，但它们不再承载裸业务语义。

## 4. 统一信封字段

建议所有控制消息兼容如下结构：

```json
{
  "version": "v1",
  "message_id": "msg_01J...",
  "trace_id": "trace_01J...",
  "session_id": "sess_01J...",
  "task_id": "task_01J...",
  "stream_id": "stream_01J...",
  "channel": "control",
  "semantic": "request",
  "name": "voice.session.open",
  "source": {
    "device_id": "glass-001",
    "device_type": "glass",
    "module": "glass-api"
  },
  "target": {
    "device_id": "server-main",
    "device_type": "server",
    "module": "server-api"
  },
  "priority": "normal",
  "reply_to": null,
  "ts": 1744262400000,
  "payload": {},
  "meta": {}
}
```

第一期不要求所有字段都必须出现。为了降低实现复杂度，建议把字段分成“必填字段”和“按需字段”。

## 5. 字段说明

### 5.1 第一期必填字段

- `message_id`
  - 单条消息唯一标识。
  - 用于去重、重试、回放保护。
- `channel`
  - 当前固定为 `control`
- `semantic`
  - 枚举：`request`、`notify`
- `name`
  - 消息名，采用点分层风格。
  - 例如：`voice.session.open`
- `source`
  - 发送方身份。
- `target`
  - 接收方身份。
- `ts`
  - 毫秒时间戳。
- `payload`
  - 业务数据。

第一期推荐最小必填集合：

- `message_id`
- `channel`
- `semantic`
- `name`
- `source`
- `target`
- `ts`
- `payload`

### 5.2 按需字段

- `version`
  - 协议版本，首版固定为 `v1`。
- `trace_id`
  - 一次完整业务链路的追踪标识。
  - 只有跨模块排障、跨设备协同明显需要时再带。
- `session_id`
  - 某个长时会话的标识。
  - 只在语音会话、设备连接会话这类长生命周期场景使用。
- `task_id`
  - 某个后台任务实例标识。
  - 只有后台任务和复杂任务编排链路必须带。
  - 第 1、2 项中的普通语音对话默认不带 `task_id`。
- `stream_id`
  - 某个流式数据上下文标识。
  - 只在与媒体流关联时使用。
- `priority`
  - 枚举建议：`low`、`normal`、`high`、`critical`
  - 只有执行侧需要抢占时再带。
- `reply_to`
  - 若本消息是响应某条消息，则写入原 `message_id`。
  - 只在需要明确对应上一条请求时使用。
- `meta`
  - 非核心扩展信息，例如调试信息、重试次数、编码说明。
  - 第一阶段能不用就不用。

## 6. 命名约束

### 6.1 消息名格式

统一采用：

`域.对象.动作`

示例：

- `device.register`
- `device.bind`
- `voice.session.open`
- `sensor.camera.capture`
- `task.create`
- `task.cancel`
- `actuator.audio.play`

### 6.2 对象域建议

- `device`
- `sensor`
- `actuator`
- `task`
- `peer_link`
- `agent`
- `tool`

## 7. 幂等与确认机制

### 7.1 幂等要求

所有 `semantic=request` 的控制消息必须支持基于 `message_id` 的幂等保护：

- 重复接收同一命令，不应创建两个任务或重复播放两次。
- 重试时应返回同一结果或同一状态。

### 7.2 确认机制

第一期默认采用“单次结果通知”，不要一开始就引入两段确认。

默认规则：

1. 发送 `request`
2. 接收方执行
3. 接收方回一条结果 `notify`

示例：

- `voice.session.open`
- `voice.session.opened`

只有以下场景再额外补“接收确认”：

- 长任务创建
- 需要明确排队成功
- 设备侧执行明显较慢

例如：

- `task.create`
- `task.created`
- `task.state.changed`

这样可以避免一开始出现大量 `accepted`、`started`、`finished` 并存，导致协议和状态同步一起变重。

## 8. 错误模型

统一错误结构建议如下：

```json
{
  "code": "DEVICE_BUSY",
  "message": "camera is already occupied by another task",
  "retryable": false,
  "details": {}
}
```

建议首批错误码：

- `INVALID_MESSAGE`
- `UNAUTHORIZED`
- `UNSUPPORTED_VERSION`
- `DEVICE_BUSY`
- `TASK_NOT_FOUND`
- `STREAM_NOT_FOUND`
- `TIMEOUT`
- `INTERNAL_ERROR`

## 9. 与旧项目的映射关系

旧项目中的这些隐式协议，应迁移为统一控制消息：

- `START` / `STOP` / `PROMPT:` 这类裸文本控制命令
- 媒体通道上的业务文本信号
- 导航状态切换、找物品切换、红绿灯检测切换

迁移后应变成：

- `voice.session.open`
- `voice.session.close`
- `agent.prompt.submit`
- `actuator.audio.play`
- `task.state.changed`

需要强调：

- `/ws_audio`、`/ws/camera`、`/stream.wav` 这类旧项目里已经验证过的流式媒体通道可以保留
- 新架构不要求把媒体流强行塞进统一 JSON
- 新架构要求的是：媒体流的建立、结束、错误恢复、任务归属必须通过统一控制消息表达
- 因此本次迁移的重点不是重写媒体传输，而是把原先散落在媒体通道里的业务控制语义迁移出来

## 10. 最小落地建议

第一阶段不要试图一次覆盖所有业务，只需要先把 envelope 真正用于：

1. 设备注册与心跳
2. 语音对话
3. 拍照工具
4. 手机与眼镜绑定

做到这一步，后续 Tool、MCP、后台任务才能在统一语义上继续扩展。

## 11. 最小状态原则

统一信封不等于统一状态中心。为了避免协议设计把实现拖进复杂状态维护，第一期建议遵守下面的限制。

### 11.1 只允许四类主体持有运行态

- 设备连接
  - 只维护 `online/offline/last_seen`
- 语音会话
  - 只维护当前是否在收片段、是否在等模型、是否在播报
- 后台任务
  - 只维护 `created/running/completed/failed`
- 播放执行
  - 只维护 `idle/playing`

### 11.2 不要持久化的状态

以下信息原则上从消息事实重建，不单独维护复杂状态机：

- 单条控制消息的中间处理态
- 普通通知消息的已读未读
- 视频流每一帧的运行状态
- 唤醒检测与端点检测的细粒度瞬时状态

### 11.3 不要建设的机制

第一期不要做：

- 通用状态机引擎
- 跨模块统一状态仓库
- 每种消息都配一套 `accepted/started/finished`
- 事件溯源式全量回放框架

### 11.4 真正需要维护的最小索引

服务端只维护这些最小运行时索引即可：

- `device_id -> 连接对象`
- `session_id -> VoiceSession`
- `task_id -> TaskRuntime`
- `stream_id -> 当前流上下文`

如果一个状态不能落到上面四类索引里，第一期通常就不应该单独维护。

对于 [第一期功能开发计划.md](/Users/elio/dev/llm-project/OpenAIglassesDemo_2/doc/stage1/plan/第一期功能开发计划.md) 第 1、2 项，进一步收敛为：

- 必须维护：`device_id -> 连接对象`
- 必须维护：`session_id -> VoiceSession`
- 必须维护：`stream_id -> 当前流上下文`
- 暂不要求：`task_id -> TaskRuntime`
