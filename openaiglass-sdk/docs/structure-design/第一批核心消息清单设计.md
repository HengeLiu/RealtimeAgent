# 第一批核心消息清单设计

## 1. 目标

本清单只覆盖第一期真正需要落地的最小消息集，不追求一次把全部消息设计完。

本清单中的所有消息都属于统一 `ControlMessage`。

语义上只区分两类：

- `request`：要求对方执行动作
- `notify`：通知事件发生或上报当前状态

目标是先支撑以下能力：

1. 设备注册与在线管理
2. 眼镜与服务器的语音对话
3. 拍照与图片解读
4. 后台任务创建与状态跟踪

## 1.1 第 1、2 项冻结范围

如果只验证设备注册和半双工语音主链路，则消息范围进一步收敛为：

- `device.register`
- `device.registered`
- `device.register.failed`
- `device.heartbeat`
- `voice.session.open`
- `voice.session.opened`
- `voice.session.close`
- `voice.session.closed`
- `sensor.audio.segment.started`
- `sensor.audio.segment.finished`
- `actuator.audio.play`
- `actuator.audio.started`
- `actuator.audio.finished`
- `actuator.audio.state`

这一阶段默认不要求：

- `device.state.report`
- `agent.prompt.submit`
- `agent.reply.final`
- `task.create`
- `task.state.changed`

这些消息仍属于后续架构范围，但不应阻塞第 1、2 项实现。

## 2. 设备注册与连接

### 2.1 注册相关

- `device.register`
  - 用途：设备首次接入注册
  - 方向：设备 -> 服务器
- `device.registered`
  - 用途：注册成功
  - 方向：服务器 -> 设备
- `device.register.failed`
  - 用途：注册失败
  - 方向：服务器 -> 设备

### 2.2 心跳与在线状态

以下消息在协议语义上都属于 `notify`：

- `device.heartbeat`
  - 用途：保活
  - 方向：设备 -> 服务器
- `device.state.report`
  - 用途：上报设备状态快照
  - 方向：设备 -> 服务器
- `device.state.changed`
  - 用途：服务器广播设备状态变更
  - 方向：服务器 -> 相关模块

## 3. 感知相关

## 3.1 语音会话与音频片段

- `voice.session.open`
  - 用途：打开一条语音会话
  - 方向：服务器/任务 -> 眼镜
- `voice.session.opened`
  - 用途：语音会话已打开
  - 方向：眼镜 -> 服务器
- `voice.session.close`
  - 用途：关闭一条语音会话
  - 方向：服务器/任务 -> 眼镜
- `voice.session.closed`
  - 用途：语音会话已关闭
  - 方向：眼镜 -> 服务器
- `sensor.audio.segment.started`
  - 用途：本地 WakeNet 唤醒成功后开始一轮语音采集
  - 方向：眼镜 -> 服务器
- `sensor.audio.segment.finished`
  - 用途：本地端点检测判定当前语音采集结束
  - 方向：眼镜 -> 服务器

建议配套的 `Stream`：

- `audio_chunk`
  - 元数据：`stream_id`、`segment_id`、`sample_rate`、`channels`、`codec`、`chunk_index`、`is_final`

说明：

- 麦克风由 `sensor-hub` 统一管理，在待命监听和当前轮采集时开启，在回复播放期间暂停
- 只有在本地 WakeNet 成功唤醒并进入当前采集窗口后，才向服务器发 `audio_chunk`
- 因此 `voice.session.open` 表达的是“开启语音会话能力”，不是“打开麦克风电源”
- 音频上行仍可沿用旧项目的 `/ws_audio` 一类流式通道，控制语义通过统一控制消息表达
- 真实音频字节不放在 `ControlMessage.payload` 里，详细格式见 [媒体流传输格式设计.md](./媒体流传输格式设计.md)

## 3.2 相机采集

- `sensor.camera.capture`
  - 用途：抓拍一张图片
  - 方向：服务器/Tool -> 眼镜
- `sensor.camera.captured`
  - 用途：抓拍完成
  - 方向：眼镜 -> 服务器
- `sensor.camera.stream.start`
  - 用途：开始视频流
  - 方向：服务器/任务 -> 眼镜
- `sensor.camera.stream.stop`
  - 用途：停止视频流
  - 方向：服务器/任务 -> 眼镜

建议配套的 `Stream`：

- `camera_frame`
  - 元数据：`stream_id`、`width`、`height`、`format`、`frame_index`

说明：

- 视频帧传输继续沿用旧项目 `ws/camera` 一类持续推流方式
- 新架构只要求把开始、停止、失败、任务归属等控制语义从视频通道中剥离出来

## 3.3 IMU

- `sensor.imu.stream.start`
- `sensor.imu.stream.stop`
- `sensor.imu.state`

建议配套的 `Stream`：

- `imu_sample`

## 4. 执行相关

## 4.1 音频播放

以下消息中，`actuator.audio.play` 与 `actuator.audio.interrupt` 属于 `request`，其余属于 `notify`：

- `actuator.audio.play`
  - 用途：播放音频资源或播放音频流
  - 方向：服务器/任务 -> 眼镜
- `actuator.audio.started`
  - 用途：开始播放
  - 方向：眼镜 -> 服务器
- `actuator.audio.finished`
  - 用途：播放结束
  - 方向：眼镜 -> 服务器
- `actuator.audio.interrupt`
  - 用途：打断当前播放
  - 方向：服务器/任务 -> 眼镜
- `actuator.audio.state`
  - 用途：上报当前播放状态
  - 方向：眼镜 -> 服务器

建议配套的 `Stream`：

- `reply_audio_chunk`
  - 元数据：`stream_id`、`sample_rate`、`channels`、`codec`、`chunk_index`、`is_final`

说明：

- 回复播报期间设备必须暂停 WakeNet 和麦克风上行
- 回复音频数据面仍走独立流式通道，不放进 `ControlMessage.payload`
- 第一版回复下行物理承载继续沿用 `/stream.wav`
- 详细格式见 [媒体流传输格式设计.md](./媒体流传输格式设计.md)

### 4.2 震动与设备控制

- `actuator.vibrate.trigger`
- `actuator.volume.set`
- `actuator.mode.set`

这部分不是第一批硬前置，但建议命名先统一。

## 5. Agent 与 Tool 相关

## 5.1 用户输入

- `agent.prompt.submit`
  - 用途：提交用户一次输入
  - 方向：眼镜 -> 服务器
- `agent.reply.delta`
  - 用途：模型文本增量
  - 方向：服务器 -> 设备/UI
- `agent.reply.final`
  - 用途：模型最终回复
  - 方向：服务器 -> 设备/UI

## 5.2 Tool 调用

- 当前阶段不把 Tool 内部调用再建成独立控制消息。
- `agent-core` 内部 Tool 调用直接在进程内完成，并通过 `CapabilityTrace` 记录。
- 若后续出现跨进程 Tool 执行需求，再单独补充 `tool.call / tool.result / tool.failed`。

## 5.3 MCP 调用

- `mcp.call`
- `mcp.result`
- `mcp.failed`

若后续引入跨进程 Tool 执行，Tool 与 MCP 的 envelope 可以完全一致，主要差异在 `target.module`。

## 6. 后台任务相关

- `task.create`
  - 用途：创建后台任务
- `task.created`
  - 用途：任务创建成功

  - 用途：启动任务
- `task.state.changed`
  - 用途：任务状态变化广播
- `task.query`

## 8. 不建议继续沿用的旧式消息

以下旧式控制语义不建议继续进入新架构：

- `START`
- `STOP`
- `PROMPT:xxx`
- `RESTART`
- 在媒体流通道里塞裸业务文本

原因很直接：

- 不能被 `agent-core` 理解
- 不能被 `backend-task-core` 标准化调度
- 不能表达任务、设备、流之间的关系
- 不能做一致的日志和测试

需要保留的旧实现经验是：

- 独立媒体流通道可以保留
- 但媒体流通道不能继续承担业务控制语义
