# 通知抢播与用户打断策略设计

更新时间：2026-04-28
对应版本：sdk-v8

## 1. 设计目标

任务通知、Agent 回复、手机视觉告警和用户打断都可能争用同一个播报通道。业务层不应直接操作播放器，也不应各自实现抢播规则。

sdk-v8 先完成通知仲裁的最小 SDK 闭环：

1. 通知请求显式声明 `interrupt_policy` 和 `resume_policy`。
2. 通知协调器输出可解释的仲裁结果。
3. 运行态快照暴露当前活动通知、待播通知和最近仲裁决策。
4. 高优先级通知可以中断已有通知播放流。

本轮不实现完整实时语音用户打断。用户语音打断需要实时收音、VAD、回声处理和播放状态联动，仍作为后续独立能力。

## 2. 通知策略字段

`NotificationRequest` 新增显式策略字段：

| 字段 | 含义 |
| --- | --- |
| `interrupt_policy` | 抢播策略。为空时兼容旧字段：`allow_interrupt=true` 等价于 `higher_priority`，否则为 `never`。 |
| `resume_policy` | 被抢播内容后续如何处理。当前默认 `drop_interrupted`，后续可扩展恢复播放。 |

当前 `interrupt_policy` 支持：

| 值 | 含义 |
| --- | --- |
| `never` | 不抢播当前活动通知。 |
| `higher_priority` | 只有优先级高于当前活动通知时抢播。 |
| `critical_only` | 只有 `priority=critical` 时抢播。 |
| `always` | 只要 `allow_interrupt=true` 就抢播。 |

## 3. 仲裁结果

`NotificationSubmitResult` 新增：

| 字段 | 含义 |
| --- | --- |
| `reason` | 本次通知被接受、排队、抢播或去重的原因。 |
| `active_request_id` | 本次提交后当前活动通知编号。 |
| `queued_position` | 通知进入待播队列时的位置。 |

典型原因：

| reason | 含义 |
| --- | --- |
| `no_active_request` | 当前设备没有活动通知，直接下发。 |
| `dedupe_key_in_window` | 去重窗口内已收到同类通知，本次丢弃。 |
| `active_request_not_interruptible` | 当前活动通知不能被本次请求抢播，本次排队。 |
| `incoming_policy_allows_interrupt` | 新通知符合抢播策略，已中断旧通知。 |
| `previous_request_completed` | 前一条通知完成后，队列下一条被放行。 |

## 4. 运行态快照

`NotificationCoordinator.build_snapshot()` 输出：

1. `active_requests`
2. `pending_requests`
3. `recent_decisions`

`VoiceRuntime.build_runtime_snapshot()` 会把与设备相关的通知状态合并到设备快照：

1. `active_notification`
2. `pending_notifications`
3. `recent_notification_decisions`

这些字段用于解释“为什么这条通知被播报、排队、抢播或去重”。

## 5. 播放中断

当高优先级通知抢播当前通知时，`VoiceRuntime` 会：

1. 找到旧通知对应的播放流。
2. 移除通知编号与播放流映射。
3. 标记旧播放流失败、完成并中止队列。
4. 下发 `actuator.audio.interrupt`。
5. 在运行态中记录 `last_playback_state=interrupted` 和原因。

当前中断只针对通知播放流，不直接抢占普通 Agent 回复。普通回复、任务通知、视觉告警之间的统一播放仲裁会在后续继续收敛。

## 6. 开发者边界

业务 Tool、Task 和 PhoneTask 应遵守：

1. 只提交结构化通知请求和优先级，不直接操作播放器。
2. 需要抢播时声明 `priority`、`allow_interrupt` 和 `interrupt_policy`。
3. 不在业务层维护通知队列、去重窗口或播放流状态。
4. 联调时通过运行态快照查看仲裁决策。

## 7. 验收口径

sdk-v8 自动化验收覆盖：

1. 相同 `dedupe_key` 的通知会被去重并记录原因。
2. 当前通知未完成时，新通知会按策略排队。
3. `critical_only` 策略下，high 通知不抢播，critical 通知抢播。
4. 运行态快照能看到活动通知、待播通知和最近仲裁决策。
5. 抢播旧通知时会下发 `actuator.audio.interrupt` 并记录中断状态。
