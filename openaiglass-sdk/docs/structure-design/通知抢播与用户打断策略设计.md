# 通知抢播与用户打断策略设计

更新时间：2026-04-28
对应版本：sdk-v15

## 1. 设计目标

任务通知、Agent 回复、手机视觉告警和用户打断都可能争用同一个播报通道。业务层不应直接操作播放器，也不应各自实现抢播规则。

sdk-v8 先完成通知仲裁的最小 SDK 闭环：

1. 通知请求显式声明 `interrupt_policy` 和 `resume_policy`。
2. 通知协调器输出可解释的仲裁结果。
3. 运行态快照暴露当前活动通知、待播通知和最近仲裁决策。
4. 高优先级通知可以中断已有通知播放流。

sdk-v15 在此基础上补齐统一播放仲裁和用户主动打断播报的半双工控制语义：

1. 普通 Agent 回复、任务通知、视觉告警统一转成 `PlaybackIntent`。
2. `PlaybackArbiter` 统一维护当前播报、待播队列和最近播放决策。
3. `user.voice.interrupt` 进入 `VoiceRuntime.handle_user_interrupt(...)`，停止当前播报并按策略清空或保留队列。
4. 运行态快照暴露 `active_playback_intent`、`pending_playback_intents` 和 `recent_playback_decisions`。

本轮仍不实现完整全双工实时语音。实时收音、VAD、回声处理和实时模型链路仍作为后续独立能力。

## 2. 通知策略字段

`NotificationRequest` 新增显式策略字段：

| 字段 | 含义 |
| --- | --- |
| `interrupt_policy` | 抢播策略。为空时兼容旧字段：`allow_interrupt=true` 等价于 `higher_priority`，否则为 `never`。 |
| `resume_policy` | 被抢播内容后续如何处理。当前默认 `drop_interrupted`，后续可扩展恢复播放。 |

当前 `interrupt_policy` 支持：

| 值 | 含义 |
| --- | --- |
| `never` | 不抢播当前活动通知。 |
| `higher_priority` | 只有优先级高于当前活动通知时抢播。 |
| `critical_only` | 只有 `priority=critical` 时抢播。 |
| `always` | 只要 `allow_interrupt=true` 就抢播。 |

## 3. 仲裁结果

`NotificationSubmitResult` 新增：

| 字段 | 含义 |
| --- | --- |
| `reason` | 本次通知被接受、排队、抢播或去重的原因。 |
| `active_request_id` | 本次提交后当前活动通知编号。 |
| `queued_position` | 通知进入待播队列时的位置。 |

典型原因：

| reason | 含义 |
| --- | --- |
| `no_active_request` | 当前设备没有活动通知，直接下发。 |
| `dedupe_key_in_window` | 去重窗口内已收到同类通知，本次丢弃。 |
| `active_request_not_interruptible` | 当前活动通知不能被本次请求抢播，本次排队。 |
| `incoming_policy_allows_interrupt` | 新通知符合抢播策略，已中断旧通知。 |
| `previous_request_completed` | 前一条通知完成后，队列下一条被放行。 |

## 4. 运行态快照

`NotificationCoordinator.build_snapshot()` 输出：

1. `active_requests`
2. `pending_requests`
3. `recent_decisions`

`VoiceRuntime.build_runtime_snapshot()` 会把与设备相关的通知状态合并到设备快照：

1. `active_notification`
2. `pending_notifications`
3. `recent_notification_decisions`

这些字段用于解释“为什么这条通知被播报、排队、抢播或去重”。

## 5. 播放中断

当高优先级通知抢播当前通知时，`VoiceRuntime` 会：

1. 找到旧通知对应的播放流。
2. 移除通知编号与播放流映射。
3. 标记旧播放流失败、完成并中止队列。
4. 下发 `actuator.audio.interrupt`。
5. 在运行态中记录 `last_playback_state=interrupted` 和原因。

sdk-v15 起，高优先级 `PlaybackIntent` 可以抢占当前普通 Agent 回复或通知播放流。旧的通知中断路径保留为兼容层，最终仍会同步到统一播放仲裁状态。

## 6. 统一播放仲裁器

`PlaybackIntent` 字段：

| 字段 | 含义 |
| --- | --- |
| `intent_id` | 播放意图编号，默认由来源和 `stream_id` 组合。 |
| `source` | 播放来源，可为 `agent_reply`、`task_notification`、`vision_alert`、`system_alert`。 |
| `device_id/session_id` | 当前播放归属设备和会话。 |
| `stream_id` | 实际音频播放流编号。 |
| `priority` | `low`、`normal`、`high`、`critical`。 |
| `interrupt_policy` | `never`、`higher_priority`、`critical_only`、`always`。 |
| `resume_policy` | 当前默认 `drop_interrupted`。 |
| `task_id` | 可选后台任务编号。 |

`PlaybackDecision` 当前支持：

| action | 含义 |
| --- | --- |
| `play_now` | 当前设备没有活动播放，立即播放。 |
| `queue` | 当前播放不能被抢占，新意图进入待播队列。 |
| `interrupt` | 新意图按策略抢占当前播放。 |
| `user_interrupt` | 用户主动打断当前播放。 |

`VoiceRuntime.build_runtime_snapshot()` 新增：

1. `active_playback_intent`
2. `pending_playback_intents`
3. `recent_playback_decisions`

这些字段与 `last_playback_state`、`last_playback_reason` 一起用于解释“为什么当前播报被播放、排队、抢播或丢弃”。

## 7. 用户主动打断

眼镜端上报：

```json
{
  "name": "user.voice.interrupt",
  "semantic": "notify",
  "payload": {
    "reason": "user_voice_interrupt",
    "clear_queue": true
  }
}
```

服务端处理语义：

1. `PlaybackArbiter.user_interrupt(...)` 先更新播放仲裁状态。
2. `VoiceRuntime` 从本地播放流表移除当前流和可选待播流。
3. 当前流被标记为 `interrupted`，迟到的 `actuator.audio.finished` 会被安全忽略。
4. 服务端向眼镜下发 `actuator.audio.interrupt`，payload 包含 `stream_id`、`reason` 和 `clear_queue`。
5. 若 `clear_queue=true`，待播队列全部丢弃；若为 false，只停止当前播报。

当前 `clear_queue=false` 只保留仲裁器中的待播队列，后续如果需要“从断点恢复播放”或“摘要补偿”，应扩展 `resume_policy`，业务层不应自行重排播放器。

## 8. 开发者边界

业务 Tool、Task 和 PhoneTask 应遵守：

1. 只提交结构化通知请求和优先级，不直接操作播放器。
2. 需要抢播时声明 `priority`、`allow_interrupt` 和 `interrupt_policy`。
3. 不在业务层维护通知队列、去重窗口或播放流状态。
4. 联调时通过运行态快照查看仲裁决策。

## 9. 验收口径

sdk-v15 自动化验收覆盖：

1. 相同 `dedupe_key` 的通知会被去重并记录原因。
2. 当前通知未完成时，新通知会按策略排队。
3. `critical_only` 策略下，high 通知不抢播，critical 通知抢播。
4. 运行态快照能看到活动通知、待播通知和最近仲裁决策。
5. 抢播旧通知时会下发 `actuator.audio.interrupt` 并记录中断状态。
6. 高优先级视觉告警可以抢占普通 Agent 回复。
7. 用户主动打断可以停止当前播报并按策略清空待播队列。
8. 运行态快照能看到 `play_now`、`queue`、`interrupt`、`user_interrupt` 决策。

## 10. 后续扩展：全双工实时语音

sdk-v15 的能力边界是统一播放仲裁和半双工用户主动打断。全双工实时语音已经拆为独立专项，见 [全双工实时语音对话设计](./全双工实时语音对话设计.md)。

全双工专项仍必须复用本设计中的 `PlaybackArbiter`。端侧 VAD、回声处理和实时模型链路的结果应转换成 `UserInterruptEvent` 或等价控制事件，不能绕过统一播放器状态。

### 10.1 统一输入模型

| 输入来源 | 统一意图类型 | 说明 |
| --- | --- | --- |
| 普通 Agent 回复 | `agent_reply` | 包括普通文本流式 TTS 分片和最终回复。 |
| Task 通知 | `task_notification` | 来自 `TaskEventBridge` 或业务 Task 的结构化通知。 |
| 手机视觉告警 | `vision_alert` | 来自手机视觉运行时的高优先级安全提示。 |
| 系统错误提示 | `system_alert` | 设备断连、权限失败、任务失败等系统事件。 |
| 用户语音打断 | `user_interrupt` | 用户主动说话、按键或端侧打断事件。 |

### 10.2 核心对象

| 对象 | 职责 |
| --- | --- |
| `PlaybackIntent` | 描述一次待播内容、来源、优先级、打断策略和恢复策略。 |
| `PlaybackLease` | 表示当前播报占用的音频通道和可恢复状态。 |
| `PlaybackArbiter` | 根据当前 lease、队列和新 intent 输出仲裁决策。 |
| `UserInterruptEvent` | 描述用户打断来源、时间、会话和处理策略。 |
| `PlaybackDecisionLog` | 记录每次播放、排队、抢播、恢复和丢弃的原因。 |

### 10.3 用户打断语义

第一版用户打断只承诺半双工语义：

1. 用户打断到达时，SDK 停止当前播报。
2. 根据当前 `resume_policy` 决定是否保留队列。
3. 如果当前播报来自普通 Agent 回复，默认丢弃剩余分片。
4. 如果当前播报来自关键系统告警，默认完成当前短提示后再进入用户输入处理。
5. 所有打断都写入运行态快照和 DEBUG 日志。

本设计不承诺已经完成全双工实时语音、回声消除或复杂 VAD。后续实时语音只需要把 VAD 结果转换为 `UserInterruptEvent`，不应绕过播放仲裁器。

### 10.4 决策输出

`PlaybackArbiter` 的决策至少包含：

| 字段 | 说明 |
| --- | --- |
| `decision` | `play_now`、`queue`、`interrupt`、`drop`、`resume`。 |
| `reason` | 人类可读且可测试的决策原因。 |
| `active_lease_id` | 当前播放租约。 |
| `interrupted_lease_id` | 被打断的播放租约。 |
| `queue_size` | 决策后的队列长度。 |
| `resume_action` | `none`、`resume_from_checkpoint`、`summarize_then_drop`。 |
