# 手机视觉资源管理设计

更新时间：2026-04-28
对应版本：sdk-v6

## 1. 设计目标

手机视觉能力会持续消费眼镜视频帧，并可能同时运行多个任务。如果每个业务任务自己维护帧率、丢帧、过载和任务结果，就会把系统资源治理扩散到业务层。

本设计把第一版手机视觉资源管理收敛到 SDK 运行时：

1. SDK 负责根据任务参数限制帧处理频率。
2. SDK 负责记录被丢弃的帧和过载原因。
3. SDK 负责把资源事件写入手机任务快照，供回放测试和联调排查。
4. 业务任务只处理真正被 SDK 分发的帧，不直接管理帧队列和资源限制。

## 2. 当前实现范围

sdk-v6 首先在 Python `PhoneRuntime` 中落地资源策略，主要服务于 `phone-mock`、设备级回放测试和服务端侧手机任务模拟。

当前已经支持：

1. `VisionTaskPolicy`
2. `vision_policy.min_frame_interval_ms`
3. `vision_policy.max_frames`
4. `vision_policy.priority` 字段透传和快照记录
5. `vision_policy.emit_overload_events`
6. `PhoneTaskSnapshot.frames_dropped`
7. `PhoneTaskSnapshot.resource_events`
8. `vision.task.overloaded` 结构化资源事件

当前暂不支持：

1. iOS 真机运行时内置模型资源池。
2. 多模型加载、卸载和内存治理。
3. 多任务优先级抢占。
4. 后台任务和前台任务之间的功耗策略。
5. 真实视频帧队列的异步背压。

这些内容将在后续 iOS 运行时资源管理迭代中继续补齐。

## 3. 任务参数

手机任务可以在启动参数中声明 `vision_policy`：

```json
{
  "stream_id": "stream_cam_001",
  "vision_policy": {
    "min_frame_interval_ms": 1000,
    "max_frames": 30,
    "priority": 10,
    "emit_overload_events": true
  }
}
```

字段说明：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `min_frame_interval_ms` | int | 同一个手机任务两次实际处理帧之间的最小间隔。 |
| `max_frames` | int | 单个任务最多允许处理的帧数，未设置或为 0 表示不限制。 |
| `priority` | int | 任务优先级，当前只记录和透传，后续用于资源仲裁。 |
| `emit_overload_events` | bool | 触发限流时是否记录 `vision.task.overloaded`。 |

为了兼容早期参数，SDK 也会读取顶层 `frame_interval_ms`、`min_frame_interval_ms`、`max_frames` 和 `priority`，但新代码应优先放入 `vision_policy`。

## 4. 资源事件

当 SDK 判断当前帧不能继续投递给任务时，会增加 `frames_dropped`，并在 `resource_events` 中记录事件：

```json
{
  "event_name": "vision.task.overloaded",
  "reason": "frame_rate_limited",
  "task_id": "phone_task_xxx",
  "task_type": "demo_phone_task",
  "stream_id": "stream_cam_001",
  "frame_ts_ms": 123456,
  "frames_processed": 1,
  "frames_dropped": 1,
  "min_frame_interval_ms": 1000,
  "max_frames": 30
}
```

当前 `reason` 取值：

| reason | 含义 |
| --- | --- |
| `frame_rate_limited` | 当前帧与上一帧实际处理时间间隔不足。 |
| `max_frames_reached` | 当前任务已经达到最大处理帧数。 |

资源事件只说明 SDK 因资源策略丢弃了帧，不代表业务能力失败。业务任务不应该把资源事件当成自己的业务结果。

## 5. SDK 运行时行为

`PhoneRuntime.process_frame(...)` 的处理顺序：

1. 按 `task_types` 过滤任务类型。
2. 按任务参数中的 `stream_id` 过滤视频流。
3. 对匹配任务执行 `VisionTaskPolicy` 检查。
4. 如果通过检查，调用业务任务 `on_frame(...)`。
5. 如果未通过检查，记录 `vision.task.overloaded`，不调用业务任务。

`process_frame(...)` 会返回所有匹配任务的快照。即使某个任务因资源策略丢帧，也会返回快照，让回放测试可以断言 `frames_dropped` 和 `resource_events`。

`process_task_frame(...)` 是指定任务的直接输入入口，也会执行同一套资源策略。

## 6. 开发者边界

业务手机任务应该遵守以下边界：

1. 不要自行维护全局帧队列。
2. 不要自行判断多个任务之间的资源优先级。
3. 不要把丢帧当成业务失败直接完成 Task。
4. 需要控制处理频率时，通过任务参数声明 `vision_policy`。
5. 需要观察资源问题时，看 `PhoneTaskSnapshot.resource_events` 和 DEBUG 日志，而不是在业务逻辑里临时打印。

真实 iOS 插件在 SDK iOS 运行时补齐统一资源管理前，应先读取服务端下发的同名 `vision_policy` 参数，主动保持与 Python `PhoneRuntime` 一致的限流语义。后续 SDK 会把这部分继续下沉到 iOS 通用运行时中。

## 7. 验收口径

sdk-v6 当前自动化验收覆盖：

1. 固定帧间隔策略下，时间间隔不足的帧不会进入业务任务。
2. 达到最大处理帧数后，后续帧不会进入业务任务。
3. 被 SDK 丢弃的帧会记录 `vision.task.overloaded`。
4. 任务快照能看到 `frames_processed`、`frames_dropped`、`resource_events` 和 `vision_policy`。

后续 iOS 运行时资源管理验收需要追加：

1. 真机插件不需要自行实现帧率限流。
2. 多个手机任务能共享同一路视频帧，并按优先级或策略降级。
3. 过载事件可以通过服务端任务事件或运行态诊断回流。
