# 统一多模态流式处理架构设计

更新时间：2026-05-01

## 1. 文档定位

本文档描述 SDK 后续统一处理文本、音频、图片三类模态的目标架构。

本文档不是当前代码的实现说明，而是对近期语音链路、Omni Realtime、Agent-Core、多模态输入、图片处理和未来打断式交互讨论后的架构收敛。实施细节见 [../stage2/plan/统一多模态流式处理实施计划.md](../stage2/plan/统一多模态流式处理实施计划.md)。

截至 2026-05-01，当前代码已先落地最小骨架：`omni_realtime` 默认链路进入 Agent-Core；`agent_core.streaming` 提供基础 `TurnEvent` / `TurnCoordinator`；`agent_core.modality` 提供图片输入规划；自由插话仍不是默认能力。

## 2. 背景问题

当前代码中，多模态处理分散在多个层级：

1. `voice-runtime` 负责收音、分段、自动抓拍、ASR、TTS、播放流和 Omni Realtime 分支。
2. `agent-core` 负责上下文、记忆、Skill、工具、Agent Loop 和普通模型调用。
3. Omni Realtime 直出链路曾在 `voice-runtime` 内部构造 prompt、tools 和 tool handler，部分绕过 `AgentFacade.handle_turn(...)`。
4. 图片既可以作为当前用户输入 asset 注入模型，也曾存在工具后置解读的思路，两种方式缺少统一策略层。
5. 输出侧同时存在模型音频直出和文本转 TTS，两者没有统一的输出事件模型。

这些问题导致：

1. 同一类能力在不同路径重复实现。
2. 有些链路无法进入 Agent-Core 的固定过程，例如上下文管理、记忆注入、工具调用和日志确认。
3. 模型能力和执行逻辑耦合，例如把是否 Omni 直接影响调用链。
4. 未来支持自由打断时，很难可靠取消旧输出、隔离旧 token、处理工具副作用和图片归属。

## 3. 设计目标

统一多模态流式处理架构的目标是：

1. 所有大模型决策都进入 Agent-Core 的统一过程。
2. 模型能力只决定输入输出适配方式，不决定业务执行逻辑。
3. 文本、音频、图片都通过统一事件流表达。
4. 节点之间默认流式传输，不能流式的节点在节点内部聚合，不把阻塞细节泄漏给上下游。
5. 图片处理同时支持直传模型和工具后置解读，由策略层根据模型能力和业务策略决定。
6. 输出侧同时支持文本输出、TTS 音频输出、模型原生音频输出和文字日志。
7. 为未来用户打断保留取消、代次隔离和副作用管理能力。

## 4. 非目标

第一阶段不追求：

1. 一次性兼容所有模型供应商的所有模态组合。
2. 在服务端实现声学回声消除。
3. 把自由插话作为默认产品能力。
4. 把模型能力探测完全自动化。
5. 重写 OpenAI Agents SDK 的 Agent Loop。

## 5. 核心原则

### 5.1 Agent-Core 永远是运行核心

无论底层模型是否支持音频、图片或音频输出，都必须保留固定过程：

1. 会话上下文管理。
2. 记忆注入。
3. Skill prompt 注入。
4. 工具 schema 暴露。
5. 工具调用循环。
6. 工具结果回填。
7. 文本版用户输入和助手输出确认。
8. 调用轨迹、模型请求和交互日志记录。

Omni、Realtime、文本模型、视觉模型都只能作为 Agent-Core 的模型适配器，而不应绕过 Agent-Core 自建一套工具和 prompt 链路。

### 5.2 模型能力和执行逻辑分离

模型能力描述模型能接收和产出什么：

1. 是否支持文本输入。
2. 是否支持音频输入。
3. 是否支持图片输入。
4. 是否支持文本输出。
5. 是否支持音频输出。
6. 是否支持流式输出。
7. 是否支持工具调用。

执行逻辑描述 SDK 必须做什么：

1. 如何归属本轮输入。
2. 是否需要 ASR。
3. 是否需要 TTS。
4. 图片直传还是工具后置解读。
5. 工具副作用如何提交。
6. 播放如何仲裁。
7. 打断如何取消。

两者通过 `AgentInputPlan` 和 `AgentOutputPlan` 连接，而不是互相硬编码。

### 5.3 节点之间只传事件

所有节点都通过事件流通信：

```python
class StreamNode:
    async def process(self, events: AsyncIterator["TurnEvent"]) -> AsyncIterator["TurnEvent"]:
        ...
```

如果节点自身不支持流式，例如批量 ASR、图片解读、非流式模型调用，它可以在内部缓存事件，等输入完整后再输出。上下游不应关心该节点内部是否阻塞。

### 5.4 每个事件必须可归属

所有事件必须携带以下字段：

1. `session_id`
2. `turn_id`
3. `generation_id`
4. `stream_id`
5. `causation_id`

`turn_id` 表示用户轮次，`generation_id` 表示同一轮中的输出代次。工具调用、模型重试、打断后续接都可能产生新的 `generation_id`。

## 6. 统一事件模型

建议定义以下事件族。

### 6.1 输入事件

1. `TurnStarted`
2. `AudioChunk`
3. `AudioEnded`
4. `TextDelta`
5. `TextFinal`
6. `ImageAssetReady`
7. `UserInputCommitted`

### 6.2 规划事件

1. `AgentInputPlanReady`
2. `ModelInputReady`
3. `ToolSetReady`
4. `DeferredAssetRegistered`

### 6.3 模型事件

1. `ModelTextDelta`
2. `ModelTextFinal`
3. `ModelAudioChunk`
4. `ModelAudioEnded`
5. `ToolCallDelta`
6. `ToolCallReady`
7. `ModelResponseCompleted`

### 6.4 工具事件

1. `ToolStarted`
2. `ToolProgressText`
3. `ToolResultDelta`
4. `ToolResultFinal`
5. `SideEffectCommitted`

### 6.5 输出事件

1. `AssistantTextDelta`
2. `AssistantTextFinal`
3. `PlaybackAudioChunk`

### 6.6 控制事件

1. `CancelTurn`
2. `BargeInStarted`
3. `NodeCancelled`
4. `OutputDiscarded`
5. `TurnFailed`
6. `TurnFinished`

## 7. 总体架构

```text
Device Event Stream
  -> DeviceIngressNode
  -> MediaNormalizeNode
  -> InputModalityNodes
  -> ModalityRouter
  -> AgentCoreNode
  -> OutputModalityNodes
  -> PlaybackSink
```

### 7.1 DeviceIngressNode

职责：

1. 接收眼镜、手机或回放端事件。
2. 把设备协议转换成 SDK 内部 `TurnEvent`。
3. 维护基础连接状态。

不负责：

1. 不做 ASR。
2. 不做图片策略判断。
3. 不调用模型。

### 7.2 MediaNormalizeNode

职责：

1. 校验音频采样率、声道、编码。
2. 将音频、图片落盘为 `MediaAssetRef`。
3. 输出 `ImageAssetReady`、`AudioChunk`、`AudioEnded` 等事件。

不负责：

1. 不决定图片是否传给模型。
2. 不决定音频是否走 ASR。

### 7.3 InputModalityNodes

输入模态节点负责把设备输入转换成 Agent-Core 可用输入。

可选节点：

1. `AsrNode`: `AudioChunk/AudioEnded -> TextDelta/TextFinal`
2. `AudioPassthroughNode`: `AudioChunk -> AudioChunk`
3. `ImagePassthroughNode`: `ImageAssetReady -> ImageAssetReady`
4. `ImageCaptionNode`: `ImageAssetReady -> TextFinal`

其中 `ImagePassthroughNode` 只负责保留图片资产，不负责判断图片直传还是工具化。

### 7.4 ModalityRouter

`ModalityRouter` 是多模态策略层。

输入：

1. 当前模型能力。
2. 当前用户输入事件。
3. 当前业务策略。
4. 当前会话上下文。
5. 可用工具列表。

输出：

```python
AgentInputPlan(
    direct_model_inputs=[...],
    deferred_assets=[...],
    enabled_tools=[...],
    required_output_modalities=[...],
)
```

职责：

1. 决定音频直传模型还是先 ASR。
2. 决定图片直传模型还是注册视觉工具。
3. 决定输出侧使用模型音频还是 TTS。
4. 保证所有路径都至少有文本输出或文本转写。

### 7.5 AgentCoreNode

AgentCoreNode 是唯一的大模型决策入口。

职责：

1. 根据 `AgentInputPlan` 组装模型输入。
2. 注入 system prompt、memory prompt 和 skill prompt。
3. 导出工具 schema。
4. 执行 Agent Loop。
5. 处理工具调用和工具结果回填。
6. 输出 `ModelTextDelta`、`ModelAudioChunk`、`ToolCallReady` 等事件。
7. 写入交互日志和模型请求快照。

AgentCoreNode 不应知道设备协议，不应直接管理播放 HTTP 流，也不应直接决定端侧打断策略。

在模型原生音频直出链路里，AgentCoreNode 还需要区分“影响当前回答的工具”和“低优先级副作用工具”。例如 `memory_search` 会影响当前回答内容，必须同步等待；`manage_memory` 写入长期记忆通常不影响当前轮可说出的内容，可以先向模型回填“已受理”，再后台完成真实写入和能力轨迹记录。这样可以避免长期记忆子 Agent 阻塞首段音频。

### 7.6 ModelAdapter

ModelAdapter 屏蔽模型供应商差异。

候选适配器：

1. `TextChatModelAdapter`
2. `AudioInputChatModelAdapter`
3. `VisionChatModelAdapter`
4. `RealtimeOmniModelAdapter`
5. `AudioOutputModelAdapter`

ModelAdapter 必须输出统一模型事件，不能把供应商事件直接泄漏到 Agent-Core 外部。

### 7.7 OutputModalityNodes

输出节点负责把 Agent-Core 输出转换成设备可播放或可展示的内容。

可选节点：

1. `TtsNode`: `ModelTextDelta -> PlaybackAudioChunk`
2. `AudioPassthroughNode`: `ModelAudioChunk -> PlaybackAudioChunk`
3. `TextLogNode`: `ModelTextDelta/Final -> 文字交互日志`
4. `TranscriptNode`: `ModelAudioOutput -> AssistantTextFinal`，如果模型提供文本 side channel。

输出侧必须保证每轮有文字版助手输出，便于日志、记忆、调试和回放测试。

### 7.8 PlaybackSink

职责：

1. 统一处理播放流注册、HTTP 下行、完成通知。
2. 接入 `PlaybackArbiter`。
3. 根据 `turn_id/generation_id` 丢弃旧输出。
4. 处理打断、排队、抢播和播放完成。

## 8. 图片处理规划

图片有两种处理方式。

### 8.1 图片直传模型

适用条件：

1. 当前模型支持图片输入。
2. 当前业务策略允许本轮带图。
3. 图片属于当前 turn，且未被标记为隐私敏感或过期。

事件流：

```text
ImageAssetReady
  -> ModalityRouter
  -> AgentInputPlanReady(direct_model_inputs includes image)
  -> AgentCoreNode
```

优点：

1. 模型可以直接结合图文或音频理解。
2. 工具调用轮次少。
3. 对视觉问答延迟更低。

风险：

1. 每轮带图会增加成本和延迟。
2. 用户没有问图片时，模型可能过度描述图片。
3. 视觉模型能力不足时，错误会直接进入主回复。

### 8.2 图片工具后置解读

适用条件：

1. 当前主模型不支持图片输入。
2. 当前策略希望按需理解图片。
3. 需要把视觉理解作为可观察工具调用。

事件流：

```text
ImageAssetReady
  -> ModalityRouter(defer image)
  -> AgentInputPlanReady(enabled_tools includes understand_current_image)
  -> AgentCoreNode
  -> ToolCallReady(understand_current_image)
  -> VisionToolNode
  -> ToolResultFinal(text=image_description)
  -> AgentCoreNode continue
```

优点：

1. 主模型可以先判断是否需要视觉。
2. 视觉调用可被记录为工具轨迹。
3. 可以让专用视觉模型负责图片解读。

风险：

1. 多一次工具调用，延迟更高。
2. 工具结果是文本摘要，可能损失图像细节。
3. 如果模型没有调用工具，就不会主动看图。

### 8.3 图片策略不属于 ImagePassthroughNode

`ImagePassthroughNode` 只负责生产或保留图片资产事件。图片直传还是工具后置，应由 `ModalityRouter` 根据模型能力和业务策略决定。

## 9. 推荐链路表达

### 9.1 文本模型链路

```text
audio -> AsrNode -> text -> AgentCoreNode(text model) -> text -> TtsNode -> audio
image -> ModalityRouter -> VisionToolNode on demand
```

### 9.2 Omni 音频输入加 TTS 链路

```text
audio -> AudioPassthroughNode -> AgentCoreNode(audio input, text output) -> text -> TtsNode -> audio
image -> ModalityRouter -> direct image or vision tool
```

### 9.3 Omni 音频直出链路

```text
audio -> AudioPassthroughNode -> AgentCoreNode(audio input, audio output, text side channel) -> AudioPassthroughNode -> audio
image -> ModalityRouter -> direct image or vision tool
```

### 9.4 文本输入加音频输出模型链路

```text
audio -> AsrNode -> text -> AgentCoreNode(text input, audio output, text side channel) -> audio
image -> ModalityRouter -> direct image or vision tool
```

## 10. 打断式交互支持

统一流式架构可以支持未来自由打断，但必须把取消和代次隔离作为基础能力。

### 10.1 主要风险

1. 旧 turn 的模型 token 或音频继续输出。
2. LLM、TTS、Realtime WebSocket 或播放 HTTP 流取消不彻底。
3. 工具副作用已经提交，不能简单回滚。
4. 图片上传完成时间晚于打断，可能归属错误。
5. 播放声被麦克风收进去，造成误打断循环。
6. 低优先级副作用工具如果同步执行，可能在首段音频前制造用户可感知静默。

### 10.2 必须具备的机制

1. 每个事件带 `turn_id` 和 `generation_id`。
2. `TurnCoordinator` 维护当前 active turn 和 active generation。
3. `PlaybackSink` 只播放当前 generation 的音频。
4. 所有节点实现 `cancel(turn_id, reason)`。
5. 不能取消的节点也必须让旧输出被下游丢弃。
6. 工具需要声明副作用策略。
7. 对不影响当前回答内容的副作用工具，允许先回填已受理事件，再后台提交真实副作用。

### 10.3 工具副作用策略

工具调用可分为：

1. `ephemeral`: 只产生临时输出，打断后可丢弃。
2. `committed`: 已创建任务、写记忆、启动导航等，不能自动回滚。
3. `confirm_required`: 执行前需要用户确认。

打断只应取消未提交输出，不应静默回滚已提交副作用。

### 10.4 产品分级

建议打断能力分阶段开放：

1. 半双工，不支持播放中语音打断。
2. 手动打断，例如按钮或触控。
3. 唤醒词打断。
4. 自由插话。

自由插话必须依赖端侧 AEC/VAD 能力成熟后再默认开启。

## 11. 与当前代码的迁移关系

当前代码中：

1. `VoiceRuntime._run_omni_realtime_reply_pipeline(...)` 应逐步迁移为 Agent-Core 的 `RealtimeOmniModelAdapter`。
2. `AgentFacade.handle_turn(...)` 应成为所有模型决策的唯一入口。
3. `AgentLoopRunner._run_direct_audio_turn(...)` 可以作为音频输入模型适配器的过渡实现。
4. 自动照片逻辑应从 `AgentFacade` 的隐式消费，逐步收敛为 `ImageAssetReady -> ModalityRouter`。
5. TTS 预热和播放流逻辑应从 Agent 回调中抽象成 `OutputModalityNode + PlaybackSink`。

## 12. 验收标准

架构落地后的最低验收标准：

1. 任意语音链路都能进入 Agent-Core 的统一日志。
2. 任意链路都能输出文字版用户输入和助手回复。
3. 图片直传和图片工具后置可由配置切换。
4. 文本模型和音频输入模型共享同一套 memory、skill、tools。
5. TTS 输出和模型音频直出共享同一套播放仲裁。
6. 打断后旧 generation 的音频不会继续播放。
7. 回放测试能验证多轮音频、图片、工具调用和播放完成。
