# iteration-v60：SDK v60 播放起始插话误触发抑制

对应对外 SDK 版本：`sdk-v60`。

## 背景

`sdk-v59` 修复了服务端插话后的旧 Omni 回复迟到写回问题。真机继续联调时发现，ESP32-S3 在播放刚开始 120 到 150 毫秒内就连续上报 `user.voice.interrupt`，表现为每次只播放一点声音就停，然后新建下一段语音，进入循环。

日志显示端侧在 `播放流首段音频已写入扬声器` 后立即出现 `AEC 检测到播放中用户插话`。这更像播放起始瞬态、扬声器回声或 AEC 参考尚未收敛造成的误触发，而不是用户真实插话。

## 本轮改动

1. `glass-esp32` 新增 `CONFIG_GLASS_BARGE_IN_GRACE_MS`，默认 900ms。播放首段 PCM 真正写入扬声器后，这个保护窗内忽略播放中的 VAD 命中。
2. `glass-esp32` 新增 `CONFIG_GLASS_BARGE_IN_MIN_SPEECH_FRAMES`，默认 6 帧。保护窗结束后，需要连续命中多帧 VAD 语音才认定为真实用户插话。
3. 保护窗内如果 VAD 命中，会清空 pre-roll，避免把播放起始回声带入下一段上行音频。
4. 新增 DEBUG 日志：`忽略播放起始保护窗内的 VAD` 和 `播放中 VAD 仍在确认用户插话`，便于后续按真机环境调整阈值。

## 验证

1. 单元静态测试覆盖新增固件配置、保护窗日志和首段扬声器写入时间戳。
2. 需要真机复测：播放开始后 900ms 内不应再立即触发 `user.voice.interrupt`；900ms 后用户持续说话约 200ms 以上仍应触发播放中插话。

## 风险和后续

1. 默认 900ms 保护窗会牺牲播放开始极短时间内的插话灵敏度，但能优先阻断当前的“播一点就停”循环。
2. 如果真机仍误触发，可以继续增大 `CONFIG_GLASS_BARGE_IN_GRACE_MS` 或 `CONFIG_GLASS_BARGE_IN_MIN_SPEECH_FRAMES`。
3. 如果真机插话太迟钝，可以先把保护窗降到 600ms，再按扬声器音量和佩戴环境调 AEC 参考。
