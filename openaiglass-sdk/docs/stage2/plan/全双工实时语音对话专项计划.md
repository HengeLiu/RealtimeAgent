# 全双工实时语音对话专项计划

更新时间：2026-04-28

当前状态：`sdk-v18` 已完成第一版开发，覆盖服务端实时会话状态机、播放仲裁贯通、WebSocket MediaFrame 入口、用户插话、迟到输出丢弃、回声候选观测和回放级单测。真实实时模型供应商 Adapter、WebRTC 传输和端侧真机 AEC/VAD 效果仍进入后续真机验收。

## 1. 文档定位

本文档用于启动 SDK 的“全双工实时语音对话”专项能力补全。它只规划三端开发框架层能力，不编写盲人业务功能、不改业务 Tool/Task。

现有语音链路已经能支撑半双工语音对话：用户说完一轮后服务端 ASR、调用模型、流式下发 TTS，播放期间暂停麦克风和唤醒监听。全双工专项要解决的是另一类系统问题：设备播放时仍能继续监听用户输入，用户可以用语音自然打断播报，服务端可以在同一会话内持续处理用户输入和模型输出。

## 2. 总目标

1. 定义全双工实时语音会话协议，覆盖上行音频、下行音频、实时事件、用户打断和会话关闭。
2. 在 SDK 层建立 `RealtimeVoiceRuntime`，统一管理实时收音、模型流、播放仲裁和会话状态。
3. 复用 `PlaybackArbiter`，让普通 Agent 回复、任务通知、视觉告警和实时语音打断进入同一仲裁入口。
4. 建立回放测试能力，能模拟用户插话、回声串音、模型输出延迟和下行播放中断。
5. 给真机联调提供明确观察点，而不是把全双工问题留给业务开发者自行处理。

## 3. 非目标

1. 不在 SDK 中写具体盲人场景业务逻辑。
2. 不在 Python 服务端手写复杂声学回声消除算法。端侧或手机侧负责尽可能提供 AEC 后音频，SDK 负责协议、状态、仲裁和回放验证。
3. 第一版不强制上 WebRTC。设备链路先支持 WebSocket 双向媒体帧，后续可替换为 WebRTC 传输。
4. 不绑定某一家实时模型厂商。SDK 通过 Adapter 层接入实时模型、流式文本模型或降级半双工路径。

## 4. 优先级

| 优先级 | 能力 | 原因 |
| --- | --- | --- |
| P0 | 实时会话协议与状态机 | 没有稳定协议，端侧、手机侧和服务端无法并行开发。 |
| P0 | 播放仲裁和用户打断贯通 | 全双工最核心体验是用户说话能打断当前播报。 |
| P0 | 回放测试断言 | 全双工问题很难靠肉眼联调，需要可重复复现。 |
| P1 | 实时模型 Adapter | 不同模型供应商差异较大，需要 SDK 统一屏蔽。 |
| P1 | 延迟与回声观测 | 首包延迟和误触发是全双工体验的关键风险。 |
| P2 | WebRTC 传输替换 | 适合后续真机网络栈稳定后再做。 |

## 5. 阶段一：设计阶段

产物：

1. 新增 [全双工实时语音对话设计](../../structure-design/全双工实时语音对话设计.md)。
2. 明确全双工会话消息、媒体帧、状态机和错误语义。
3. 明确端侧 AEC/VAD 的 SDK 边界：端侧输出结构化事件，服务端不直接实现声学算法。
4. 明确实时模型 Adapter 与半双工降级路径。
5. 明确全双工回放测试需要记录和断言的事件字段。

完成标准：

1. 端侧、手机侧、服务端都能按同一协议拆分开发。
2. 文档明确哪些能力属于 SDK，哪些能力属于端侧硬件或模型供应商。
3. 文档能解释全双工与现有半双工语音链路如何共存。

## 6. 阶段二：开发阶段

开发方案见 [全双工实时语音对话开发方案](./全双工实时语音对话开发方案.md)。

计划分为六个迭代：

1. 迭代 A：补协议模型、事件类型、运行态快照字段。
2. 迭代 B：新增服务端 `RealtimeVoiceRuntime` 骨架和会话状态机。
3. 迭代 C：接入 `PlaybackArbiter`，打通实时用户打断和下行播放中断。
4. 迭代 D：新增实时模型 Adapter 抽象和半双工降级 Adapter。
5. 迭代 E：补回放测试夹具、延迟断言和回声误触发断言。
6. 迭代 F：补端侧/手机侧 SDK 协议包和真机联调脚本。

每个迭代完成后必须更新 SDK 文档、测试说明和迭代记录。只有出现可供功能开发团队使用的新 SDK 版本时，才更新 `openaiglass-for-blind/sdk-version` 和开发指南。

## 7. 阶段三：验收阶段

验收方案见 [全双工实时语音对话验收方案](./全双工实时语音对话验收方案.md)。

专项完成标准：

1. 半双工语音链路继续可用，原有 `/ws_audio` 和播放流不被破坏。
2. 播放期间用户说话可以触发结构化 `user_interrupt`，并停止或压低当前播报。
3. 回放测试能证明普通回声不会误判为用户打断。
4. 运行态快照能看到实时会话状态、播放仲裁状态、最近打断事件和关键延迟指标。
5. 真机联调能给出端侧、手机侧、服务端各自的启动顺序和观察点。

## 8. 风险与处理

| 风险 | 处理 |
| --- | --- |
| 端侧 AEC 能力不足导致喇叭串音 | SDK 接收 `echo_suppressed`、`barge_in_confidence` 等结构化字段，并提供回声注入回放测试。 |
| 实时模型供应商协议差异大 | 通过 Adapter 层统一为 SDK 内部事件，不把供应商事件直接暴露给业务层。 |
| WebSocket 双向媒体帧延迟不稳定 | 第一版保留可测试链路，后续在传输层替换为 WebRTC。 |
| 用户打断与高优先级告警冲突 | 继续由 `PlaybackArbiter` 统一仲裁，不允许业务层绕过播放器状态。 |
