# 第二期下半程 - SDK 公共契约与 SDK运行时 产品化收口计划

## 1. 文档定位

本文档不是定义独立的新一期开发计划，而是对第二期后半段剩余工作的进一步拆解。

它服务于当前主计划：

1. [第二期-SDK核心运行时与开发者扩展面产品化开发计划.md](/Users/elio/dev/llm-project/OpenAIglassesDemo_2/doc/stage2/plan/第二期-SDK核心运行时与开发者扩展面产品化开发计划.md)

本文档要解决的问题是：

1. 第二期在完成 `find_object` 官方样例最小闭环后，还剩哪些真正影响 SDK 产品化落地的工作。
2. 哪些工作虽然看起来像“下一期方向”，但本质上仍然是第二期的收口项。
3. 第二期结束前，SDK 至少要收敛到什么程度，才算真正形成对外可理解、可扩展的开发者使用面。

结论先行：

1. 公共契约收口，仍属于第二期。
2. phone / glass 的 SDK运行时 产品化收口，仍属于第二期。
3. 契约级测试和兼容性回归补齐，仍属于第二期。
4. 第二个官方样板能力，不应作为当前文档主目标，而应放到下一期规划中。

## 2. 当前阶段判断

第二期当前已经完成：

1. `openaiglass-sdk/server-python/openaiglasses` 包骨架。
2. `DeviceGroupRuntime / DeviceGroupContext`。
3. `BaseTool / BaseTask / BasePhoneTask / BasePhoneProcessor / BaseSensorProvider`。
4. `find_object` 官方样例最小闭环。
5. `ScenarioRunner` 最小场景回放。
6. 服务端与手机端的大部分 `find_object` 业务剥离。

但第二期还没有完全结束，原因在于以下三个问题仍直接影响 SDK 是否真正可交付给开发者：

1. **公共契约仍偏隐式**
   - 当前开发者主要通过代码、样例和测试去猜测哪些对象和字段是稳定的。
   - 这会直接影响外部开发者如何安全扩展 SDK。
2. **SDK运行时还没有完全能力无关化**
   - 根目录层面的 `find_object` 业务耦合已大幅减少，但 SDK运行时 边界仍未完全稳定。
   - 如果这一点不收口，第二期说“框架层和业务扩展层已经隔离”就还不够扎实。
3. **回放测试还没有完全产品化**
   - 当前已经能做最小闭环验证，但还没有形成“公共契约可回归、样板能力可兼容”的稳定测试面。
   - 这会直接影响第二期对外的可用性判断。

所以，第二期后半段的核心目标不是再加一个业务能力，而是把上述三件事收干净。

## 3. 第二期下半程收口目标

第二期后半程建议只聚焦以下三类目标。

### 3.1 目标一：公共契约收口

目标不是做一套完整的长期版本治理体系，而是先把第二期已经形成事实依赖的公共面收口出来。

本阶段至少要回答清楚：

1. 哪些对象模型属于 SDK 对外公共面。
2. 哪些消息和事件格式属于开发者可以依赖的稳定面。
3. 哪些字段允许后续增加，哪些字段不能随意重命名或删改。

建议先收敛的公共契约范围：

1. `DeviceGroup / DeviceEndpoint / DeviceGroupContext`
2. 设备注册和绑定结果的结构化视图
3. 控制消息信封中的通用字段
4. 手机任务启动、停止与事件上报格式
5. 任务运行态快照
6. `SensorReading`
7. 场景 manifest 的最小格式

第二期验收口径：

1. 这些对象和格式必须有统一代码落点，不再散落在各处隐式字典里。
2. 必须有一份说明文档讲清楚哪些是公共面，哪些仍是内部实现细节。
3. 后续如果修改这些对象或格式，必须有对应回归测试可以拦截变化。

### 3.2 目标二：SDK运行时产品化收口

目标不是完成手机和眼镜端最终发布形态，而是把它们收口成真正能力无关的 SDK运行时。

本阶段至少要达到：

1. 手机 SDK运行时 只负责连接、视频接收、手机任务承载、事件上报和配置。
2. 眼镜 SDK运行时 只负责注册、媒体采集、媒体上行、音频播放和控制消息处理。
3. SDK运行时 默认不认识 `find_object`，也不应内建未来其他业务能力。

第二期验收口径：

1. 根目录 `openaiglass-sdk/phone-ios` 和 `glass` 中不再保留具体业务词汇和业务流程分支。
2. 官方样例能力接入时，不需要继续修改 SDK运行时 底层逻辑。
3. 文档中要明确“SDK运行时负责什么、能力负责什么、SDK 公共层负责什么”。

### 3.3 目标三：测试产品化收口

目标不是在第二期就建立完整兼容矩阵，而是把当前测试从“样例能跑”提升到“开发者可以依赖”。

本阶段至少要补齐：

1. 公共契约相关的金样测试。
2. 官方 `find_object` 样例相关的兼容性回归。
3. `ScenarioRunner` 的 manifest 校验和场景校验继续稳定化。
4. 预检脚本纳入更完整的 SDK 级检查项。

第二期验收口径：

1. 开发者修改 SDK 公共对象或消息时，能被测试及时发现。
2. 第二期官方 `find_object` 样例可以通过统一回放与预检命令验证。
3. 第二期结束时，SDK 至少具备一套可重复执行的离线验证入口。

## 4. 不应纳入当前文档主目标的内容

以下内容虽然与未来 SDK 演进有关，但不建议放入第二期下半程主目标：

1. 第二个官方样板能力
2. 完整导航产品能力
3. 长期版本治理体系
4. 完整 Android / iOS 原生 SDK 发布与打包
5. 插件市场、能力包分发与远程升级

原因：

1. 这些事项更偏“下一期新增能力与长期产品化能力”。
2. 如果现在把这些内容一起纳入，会稀释第二期最关键的收口任务。

## 6. 实施顺序建议

第二期后半段建议按以下顺序收口：

1. 先做公共契约收口
   - 因为 SDK运行时 边界和测试边界都需要先知道“哪些是公共面”。
2. 再做 SDK运行时 产品化收口
   - 在契约清晰后，才好稳定 SDK运行时 职责。
3. 最后做测试产品化收口
   - 在契约和 SDK运行时 边界基本稳定后，再把测试固化下来。

不建议的做法：

1. 一边继续加新样板能力，一边再回头收口 SDK运行时。
2. 在没有明确公共面的情况下先铺大规模兼容性测试。

## 7. 任务清单

### 7.1 公共契约收口任务

1. 盘点当前 `DeviceGroup`、控制消息、任务事件、手机事件上报和场景 manifest 的真实使用面。
2. 把重复的隐式字典结构收敛到统一代码落点。
3. 新增 `SDK公共契约设计.md`，明确公共面和内部实现面的边界。
4. 为公共契约补最小金样测试。

### 7.2 SDK运行时产品化收口任务

1. 盘点 `openaiglass-sdk/phone-ios` 和 `glass` 中剩余的业务词汇与能力耦合点。
2. 把仍然残留在 SDK运行时 中的业务逻辑继续迁回 `openaiglass-for-blind/`。
3. 新增手机 SDK运行时 与眼镜 SDK运行时 职责说明文档。
4. 补 SDK运行时 通用行为测试，避免未来新增能力又重新侵入 SDK运行时。

### 7.3 测试产品化收口任务

1. 为第二期官方样例补契约级测试目录。
2. 补 `find_object` 相关兼容性回归资产。
3. 将契约测试纳入 `run_sdk_preflight`。
4. 明确第二期统一推荐的离线验证命令。

## 8. 验收命令建议

第二期下半程完成后，至少应统一支持以下验证命令：

```bash

```

## 9. 第二期最终判断标准

第二期结束前，应至少可以稳定回答以下问题，而且答案应为“是”：

1. 开发者是否已经能看清楚 SDK 的最小公共面是什么。
2. `find_object` 官方样例是否已经真正运行在 SDK 之上，而不是依赖 SDK运行时 内建业务逻辑。
3. phone / glass 的 SDK运行时 是否已经基本能力无关化。
4. 开发者是否已经可以在不依赖真机的前提下，做第一轮样例级和契约级验证。

如果上述四个问题仍有明显一项不能回答为“是”，则第二期仍未真正收口完成。
