# SDK 欠缺能力优先级优化工作计划

更新时间：2026-04-28

## 1. 文档定位

本文档用于承接 `SDK对功能开发支持情况的说明.md` 中“存在欠缺”的 SDK 能力，并按照当前已经确定的优先级拆成设计、开发、验收三个阶段。

本轮只处理以下能力，未列出的欠缺项暂时不做：

1. 手机视觉执行框架的资源管理
2. 普通文本流式和 TTS 首包延迟
3. 通知、抢播和用户打断策略
4. 多设备组织和账号级管理
5. Skill Runtime
6. 任务持久化生产化
7. 回放测试断言能力
8. iOS 和 ESP32 SDK 打包形态

本计划仍然遵守 SDK 与业务边界：

1. SDK 只提供三端开发框架、运行时、公共契约、测试支撑和开发者扩展面。
2. 不在 SDK 中实现盲人导航、找物、过街、盲道识别等具体业务能力。
3. `openaiglass-for-blind` 只作为 SDK 使用方和官方样例参考，不作为本轮 SDK 开发落点。

## 2. 总体推进原则

本轮优化不建议一次性大改所有模块，而应按优先级做成连续的小迭代。每个能力必须先完成设计边界，再进入代码开发，最后用自动化测试、回放测试或真机前检查完成验收。

优先级判断如下：

1. 手机视觉资源管理、文本流式、通知抢播三项直接影响真实场景体验，应优先处理。
2. 多设备组织和账号级管理会影响后续绑定、权限和日志归属，应在运行时体验稳定后处理。
3. Skill Runtime、任务持久化、回放断言属于开发效率和长期可维护性，应在核心运行链路边界清楚后推进。
4. iOS 和 ESP32 打包形态排在最后，因为它依赖公共契约和端侧运行时接口稳定。

## 3. 阶段一：设计阶段

目标：把每个欠缺能力的职责边界、公共接口、数据模型、运行时状态和测试口径先设计清楚，避免在代码中临时扩散系统概念。

### 3.1 手机视觉执行框架的资源管理

设计目标：

1. 定义手机视觉任务的统一资源模型，包括相机帧订阅、模型实例、推理并发、帧率、超时和取消。
2. 定义任务优先级与资源冲突处理规则，例如单任务独占、多任务共享帧、后台低频任务和前台高频任务。
3. 定义手机视觉结果事件的公共结构，避免每个业务任务自定义不可复用的结果格式。

设计产物：

1. `手机视觉资源管理设计.md`
2. `PhoneVisionRuntime`、`FrameSubscription`、`VisionResourceLease`、`VisionTaskPolicy` 的公共接口草案
3. 手机任务事件扩展草案，例如 `vision.frame.processed`、`vision.result.detected`、`vision.task.overloaded`

不做内容：

1. 不实现具体 YOLO、盲道、红绿灯或找物算法。
2. 不内置具体业务模型文件。

### 3.2 普通文本流式和 TTS 首包延迟

设计目标：

1. 打通普通文本 delta 从 AgentCore 到 TTS 的端到端流式路径。
2. 定义文本分段、句子缓冲、首包触发、TTS 队列和播放状态之间的协作方式。
3. 明确流式回复与工具调用、图片理解、任务事件插话之间的状态关系。

设计产物：

1. `普通文本流式与TTS首包延迟优化设计.md`
2. `ReplyDeltaStream`、`TtsChunkScheduler`、`PlaybackQueue` 的接口草案
3. 首包延迟、首句延迟、完整播报耗时的观测指标定义

不做内容：

1. 不在本阶段实现全双工实时语音。
2. 不承诺用户语音打断已经可用，打断策略由下一项统一设计。

### 3.3 通知、抢播和用户打断策略

设计目标：

1. 建立统一的播放仲裁模型，覆盖 Agent 回复、Task 通知、手机视觉告警、系统错误提示。
2. 定义通知优先级、去重、合并、排队、抢播、取消和恢复播报的状态机。
3. 定义用户打断事件的输入来源和处理语义，为后续实时语音预留接口。

设计产物：

1. `通知抢播与用户打断策略设计.md`
2. `NotificationPolicy`、`PlaybackArbiter`、`InterruptSignal`、`PlaybackState` 的接口草案
3. 通知事件公共字段，例如 `priority`、`dedupe_key`、`interrupt_policy`、`resume_policy`

不做内容：

1. 不实现完整实时语音收音打断。
2. 不让业务 Task 直接控制播放器抢占。

### 3.4 多设备组织和账号级管理

设计目标：

1. 定义账号、设备、设备组、绑定关系、会话和日志归属的最小模型。
2. 明确本地开发模式与生产模式的差异，避免把账号体系强制引入本地回放。
3. 定义权限检查位置，确保 Tool、Task、PhoneTask 获取设备能力时不绕过设备组授权。

设计产物：

1. `多设备组织与账号级管理设计.md`
2. `DeviceDirectory`、`AccountIdentity`、`DeviceOwnership`、`DeviceGroupBinding` 的接口草案
3. 本地开发默认账号和测试账号策略

不做内容：

1. 不实现完整商业账号系统。
2. 不实现外部用户中心、支付、组织管理后台。

### 3.5 Skill Runtime

设计目标：

1. 明确 Skill 与 Tool、Task、MCP 的关系：Skill 负责能力说明、上下文约束、工具白名单和会话态，不替代 Tool/Task。
2. 定义 Skill 加载、激活、读取、退出和审计流程。
3. 定义 `read_skill` 工具与 AgentCore 的集成边界。

设计产物：

1. 更新 `Skill Runtime设计.md`
2. `SkillManifest`、`SkillSessionState`、`SkillToolPolicy`、`SkillAuditEvent` 的接口草案
3. Skill 目录规范和最小样例

不做内容：

1. 不把业务功能直接写进 SDK Skill 样例。
2. 不做插件市场和远程 Skill 分发。

### 3.6 任务持久化生产化

设计目标：

1. 把当前 JSON 快照能力升级为可替换存储层，支持数据库、文件和内存三种实现。
2. 定义任务事件幂等、恢复、过期清理和失败补偿语义。
3. 明确 TaskRuntimeManager 与持久化层的接口边界。

设计产物：

1. `任务持久化生产化设计.md`
2. `TaskStore`、`TaskEventStore`、`TaskSnapshotStore` 的接口草案
3. 任务恢复和事件重放测试口径

不做内容：

1. 不在第一版引入复杂分布式锁或多实例抢占。
2. 不绑定某一个具体数据库作为唯一实现。

### 3.7 回放测试断言能力

设计目标：

1. 把当前“能跑通”的回放升级为“可声明预期、可断言结果、可生成报告”的测试框架。
2. 定义场景输入、设备事件、模型替身、任务事件、最终断言的统一 manifest。
3. 让功能开发团队可以用 SDK 回放测试验证自己的 Tool、Task、PhoneTask。

设计产物：

1. 更新 `SDK测试架构与样例回放设计.md`
2. `ScenarioExpectation`、`ReplayAssertion`、`ReplayReport` 的接口草案
3. 场景 manifest v2 草案

不做内容：

1. 不追求模拟所有真实硬件细节。
2. 不用回放测试替代真机联调。

### 3.8 iOS 和 ESP32 SDK 打包形态

设计目标：

1. 明确 iOS SDK 的发布方式，例如 Swift Package、XCFramework 或示例 App 内源码依赖。
2. 明确 ESP32 SDK 的发布方式，例如 ESP-IDF component、示例工程和配置模板。
3. 定义端侧版本与 Python SDK 版本的兼容规则。

设计产物：

1. `iOS与ESP32 SDK打包形态设计.md`
2. iOS 包结构、ESP-IDF component 结构、版本兼容矩阵草案
3. 端侧安装和升级验收清单

不做内容：

1. 不在公共契约稳定前做正式外部发布。
2. 不把业务样例编进 SDK 默认包。

## 4. 阶段二：开发阶段

目标：按优先级逐项实现 SDK 能力，每项都要求代码、文档、测试同时落地。开发顺序不应跳过高优先级能力，除非前置依赖确实阻塞。

### 4.1 第一批迭代：运行体验主链路

覆盖优先级：

1. 手机视觉执行框架的资源管理
2. 普通文本流式和 TTS 首包延迟
3. 通知、抢播和用户打断策略

开发任务：

1. 在手机运行时中增加视觉任务资源管理层，统一处理帧订阅、帧率限制、任务优先级和过载事件。
2. 在服务端 AgentCore 到 VoiceRuntime 之间增加普通文本 delta 流式传递和 TTS 分块调度。
3. 收敛 `NotificationCoordinator`，引入播放仲裁层，统一处理普通回复、任务通知和视觉告警。
4. 为上述三项增加 DEBUG 级观测日志，日志字段至少包含 `session_id`、`task_id`、`device_id`、`stream_id` 和事件阶段。

开发验收前置条件：

1. 不修改 `openaiglass-for-blind` 业务实现来绕过 SDK 能力。
2. 所有新增公共对象必须有契约测试或单元测试。
3. 所有新增运行时状态必须能在调试日志或运行态快照中观察。

### 4.2 第二批迭代：设备组织和能力扩展面

覆盖优先级：

1. 多设备组织和账号级管理
2. Skill Runtime

开发任务：

1. 增加设备目录和设备归属模型，支持本地开发默认账号、固定设备组和基础权限检查。
2. 把设备注册、绑定、任务创建、通知提交和日志归属接入统一设备组织模型。
3. 完成 Skill 加载、激活、读取、工具白名单、会话态和审计事件。
4. 将 Skill Runtime 接入 AgentCore，但保持 Tool、Task、MCP 仍是实际能力执行面。

开发验收前置条件：

1. 本地单设备组开发模式不能被账号模型复杂化。
2. 设备权限失败必须返回结构化错误，不能静默降级。
3. Skill 启用与禁用必须有可回放测试覆盖。

### 4.3 第三批迭代：稳定性和开发者效率

覆盖优先级：

1. 任务持久化生产化
2. 回放测试断言能力

开发任务：

1. 引入可替换 `TaskStore`，保留内存和文件实现，预留数据库实现。
2. 增加任务事件幂等键、恢复流程、过期清理和失败补偿日志。
3. 升级回放 manifest，支持输入事件、期望任务状态、期望通知、期望 Tool 调用、期望设备事件。
4. 生成结构化回放报告，便于功能开发团队定位失败点。

开发验收前置条件：

1. 旧场景回放需要保持兼容，不能因为 manifest v2 直接失效。
2. 任务恢复必须能证明重启前后的任务状态和事件日志一致。
3. 回放失败报告必须指出失败阶段，而不是只返回整体失败。

### 4.4 第四批迭代：端侧 SDK 发布形态

覆盖优先级：

1. iOS 和 ESP32 SDK 打包形态

开发任务：

1. 整理 iOS 运行时为可复用包结构，优先评估 Swift Package，必要时再补 XCFramework。
2. 整理 ESP32 运行时为 ESP-IDF component 或可复用组件目录。
3. 补齐端侧示例工程、版本兼容说明和安装脚本。
4. 确保默认包不包含 `openaiglass-for-blind` 的具体业务能力。

开发验收前置条件：

1. Python SDK、iOS SDK、ESP32 SDK 的版本兼容关系清楚。
2. 新开发者可以按文档安装端侧 SDK 并跑通最小注册、心跳和媒体链路。
3. 打包产物不会反向依赖业务目录。

## 5. 阶段三：验收阶段

目标：每批迭代都必须有独立验收，全部完成后再做总体验收。验收重点不是“测试全绿”，而是确认 SDK 是否真正把系统能力封装起来，让功能开发团队不需要处理底层细节。

### 5.1 手机视觉资源管理验收

自动化验收：

1. 单任务视觉处理：固定视频帧输入后，手机任务按预期收到帧并产生结构化事件。
2. 多任务共享视频帧：同一 `stream_id` 下多个任务可以按策略共享帧。
3. 过载保护：超过帧率或并发限制时产生结构化过载事件，不导致任务失控。

人工验收：

1. 功能开发者不需要直接管理帧队列、模型并发或相机流订阅。
2. 运行态快照和 DEBUG 日志可以定位任务是否限流、丢帧或过载。

### 5.2 普通文本流式和 TTS 首包延迟验收

自动化验收：

1. 普通文本回复能以 delta 或分段形式进入 TTS 调度层。
2. 首包延迟指标可记录，并出现在调试日志或测试报告中。
3. 工具调用前后不会打乱普通文本分段和播放顺序。

人工验收：

1. 普通问答不再必须等待完整模型回复后才开始 TTS。
2. 如果 TTS 服务失败，错误能结构化回传，不会卡住播放队列。

### 5.3 通知、抢播和用户打断策略验收

自动化验收：

1. 低优先级通知进入队列，不打断当前播报。
2. 高优先级通知按策略抢播，并记录被打断的播放状态。
3. 重复通知按 `dedupe_key` 去重或合并。

人工验收：

1. 业务 Task 只提交通知事件，不直接操作播放器。
2. 播放仲裁日志能解释为什么某条通知被播放、排队、合并或丢弃。

### 5.4 多设备组织和账号级管理验收

自动化验收：

1. 本地默认账号可以继续跑通单眼镜、单手机、单服务端闭环。
2. 非同一设备组的 Task 不能访问对方设备能力。
3. 设备注册、绑定、任务创建和日志都能带上账号或设备组归属。

人工验收：

1. 本地开发不需要复杂账号配置。
2. 多设备场景下，运行态快照可以清楚展示账号、设备组和绑定关系。

### 5.5 Skill Runtime 验收

自动化验收：

1. Skill 可以被加载、读取、激活和退出。
2. 激活 Skill 后，AgentCore 只能使用该 Skill 允许的工具集合。
3. Skill 会话态可以被保存和恢复。

人工验收：

1. Skill 不直接承载业务执行逻辑，而是组织 Tool、Task 和 MCP 的使用边界。
2. 功能开发团队可以通过一个最小 Skill 样例理解如何组织复杂能力。

### 5.6 任务持久化生产化验收

自动化验收：

1. 创建任务、写入事件、保存快照、重启恢复后，任务状态一致。
2. 重复事件不会导致任务状态重复推进。
3. 过期任务可以被清理，并留下可排查日志。

人工验收：

1. 任务存储实现可替换，业务 Task 不依赖具体存储。
2. 恢复失败时能清楚看到失败任务、失败阶段和恢复策略。

### 5.7 回放测试断言能力验收

自动化验收：

1. manifest v1 旧场景继续可运行。
2. manifest v2 可以声明任务状态、通知、设备事件、Tool 调用等预期结果。
3. 失败报告能定位到具体断言和事件阶段。

人工验收：

1. 功能开发团队可以用回放测试描述一次完整业务闭环。
2. 回放测试支持暴露问题，而不是只给出通过或失败的简单结果。

### 5.8 iOS 和 ESP32 SDK 打包形态验收

自动化验收：

1. iOS SDK 包或示例工程可以独立构建。
2. ESP32 SDK component 或示例工程可以通过基础编译检查。
3. 端侧包不包含业务能力默认依赖。

人工验收：

1. 新开发者能按文档完成 iOS、ESP32、Python 三端最小安装。
2. 版本兼容矩阵能说明哪一版 Python SDK 对应哪一版端侧 SDK。

## 6. 总体验收命令建议

每批迭代完成后至少执行：

```bash
uv run python script/run_sdk_preflight.py --report logs/sdk-preflight-priority-plan.json
uv run python script/run_sdk_contract_tests.py
uv run python script/run_sdk_scenario.py --scenario-dir testdata/scenario --pretty
```

涉及 Python SDK 变更时追加：

```bash
uv run python -m pytest openaiglass-sdk/server-python/tests server/test/contracts -q
```

涉及端侧 SDK 打包时追加：

```bash
python script/run_sdk_package_check.py
```

真机联调前追加：

```bash
bash script/sync_sdk_live_config.sh
bash script/run_sdk_live_check.sh --report logs/sdk-live-check-priority-plan.json
```

如果其中某些命令在当前分支尚不存在，应在对应迭代中补齐，不能只在文档中列为验收要求。

## 7. 完成判定

本计划完成时应达到以下状态：

1. 功能开发团队可以开发手机视觉任务，但不需要自行管理帧调度、资源限流和任务过载。
2. 普通文本回复具备可观测的流式 TTS 路径，首包延迟可以被记录和回归。
3. Agent 回复、任务通知、视觉告警和用户打断有统一仲裁模型。
4. SDK 能区分账号、设备、设备组和运行时会话，并保持本地开发模式简单。
5. Skill Runtime 可以组织复杂能力，但不污染业务执行面。
6. 任务状态可以在服务重启后恢复，业务 Task 不依赖具体存储。
7. 回放测试可以写预期、做断言、生成报告。
8. iOS 和 ESP32 SDK 有清晰的安装、构建和版本兼容方式。
