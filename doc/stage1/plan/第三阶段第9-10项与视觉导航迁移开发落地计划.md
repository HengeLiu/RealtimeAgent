## 1. 文档目标与范围

本文档用于承接以下两份既有计划文档之后的后续开发阶段：

1. [第一期前三项开发落地计划.md](/Users/elio/dev/llm-project/OpenAIglassesDemo_2/doc/stage1/plan/第一期前三项开发落地计划.md)

本文档覆盖以下核心内容：

1. 第 9 项：手机设备注册到服务器，并实现手机与眼镜一对一绑定。
2. 第 10 项：允许大模型通过工具创建眼镜与手机直连的后台任务。

2. 完整的室外导航产品化体验，例如最后 10 米引导、复杂岔路决策、全套安全策略。
3. 手机端正式 App 产品化界面、账号体系、远程配置中心。
4. 所有旧项目视觉工作流一次性全部迁移完成。

## 2. 本阶段要解决的核心问题

前两阶段完成后，当前仓库已经具备：

1. 眼镜与服务器的注册、语音会话与播报主链路。
2. `agent-core`、`Tool / MCP`、`backend-task-core` 的最小运行时。
3. 单次真实抓拍图片回传与图片解读。
4. 计时器类后台任务最小闭环。

但仍存在以下关键缺口：

1. 手机端当前仍只有最小待机入口，没有真实 `phone-api` 与任务运行时。
2. 旧项目中依赖持续视觉流的核心能力仍停留在服务端单体实现，尚未迁到手机端。
3. 眼镜与手机之间还没有统一的直连准备、建立、保活和释放机制。
4. 导航当前主要停留在“地图查询与路线准备”层，没有真正进入执行期任务。
5. 相机持续视频流还没有收敛到新架构约定的 `/ws/camera + MediaFrame` 数据面。

因此，第三阶段的目标不是简单补第 9、10 项，而是要把“手机加入后的视觉执行期主链路”真正搭起来。

## 3. 阶段规划

| 阶段 | 阶段目标 | 里程碑 |
| --- | --- | --- |
| Phase I | 手机接入与双设备绑定落地 | 手机可完成注册，服务器可维护 `glass <-> phone` 绑定关系 |
| Phase J | 眼镜-手机直连视频任务落地 | Agent 可创建 `phone_video_link_task`，手机页面可实时回显眼镜视频流 |
| Phase K | 手机端视觉能力最小迁移闭环 | 至少 1 个旧项目视觉能力迁移到手机端并完成语音反馈闭环 |
| Phase L | 导航执行期任务最小闭环 | `navigation_task` 可创建、运行、查询、取消，并能串联地图、手机视觉与端侧通知 |

## 4. 总体实施原则

1. 手机端接入必须遵循现有统一 `ControlMessage / MediaFrame` 协议，不再引入老项目式隐式字符串命令。
2. 视觉能力迁移优先迁“最小可闭环能力”，不追求一次迁完全部旧工作流。
3. 旧项目中的 YOLO、视觉状态机和播报策略要拆分为：
   - 手机端本地 Tool 或 Task
   - 服务端 `backend-task-core` 任务模板
   - 眼镜端 `sensor-hub / actuator-hub` 协作
4. 导航必须区分“路线准备”和“执行期任务”，前者主要属于 `agent-core + MCP`，后者主要属于 `backend-task-core`。
5. 眼镜与手机的直连关系必须由服务端统一协调和登记，不能让两端各自私自连通后失去可观测性。
6. 本阶段所有跨设备能力都必须给出跨设备联调方案，至少覆盖：
   - 服务端启动
   - 手机端启动
   - 眼镜端启动
   - 日志观察点
   - 异常断链恢复
7. 自动化测试优先覆盖协议、任务状态机、网关编排与 mock 视觉结果；真机联调用于验证跨设备真实链路。

## 5. 工作分解（WBS）

## 5.1 Phase I：手机接入与双设备绑定

### I1. `phone-api` 最小接入边界

任务：

1. 建立手机端可运行主入口，不再只是待机打印。
2. 实现手机到服务器的控制连接。
3. 实现手机侧 `device.register`、`device.heartbeat`。
4. 为手机侧预留任务接入点与设备状态上报点。

交付物：

1. 手机端最小运行时入口。
2. 手机端控制连接处理器。
3. 手机端配置项与启动说明。

完成定义（DoD）：

1. 手机可像眼镜一样注册到服务器。
2. 服务端运行态中可区分在线眼镜和在线手机。
3. 手机侧日志可按 `device_id / message_id / session_id` 追踪。

---

### I2. 设备目录与绑定关系管理

任务：

1. 服务端扩展设备索引，支持 `glass` 与 `phone` 两种设备类型同时在线。
2. 落地 `device.bind` 或等价绑定管理接口。
3. 维护 `glass_device_id -> phone_device_id` 的一对一绑定关系。
4. 定义绑定冲突、重复绑定、解绑与离线后的状态规则。

交付物：

1. 设备绑定关系存储模块。
2. 绑定管理接口与运行态查询接口。

完成定义（DoD）：

1. 服务端可明确知道某副眼镜当前绑定哪台手机。
2. 任一端离线时，绑定状态与可用性判断清晰可查。
3. 重复绑定和冲突绑定会返回明确结构化错误。

---

### I3. 手机接入测试与联调

任务：

1. 单元测试：设备类型识别、绑定校验、重复绑定拦截。
2. 集成测试：手机注册、眼镜注册、绑定建立、断链后状态变化。
3. 联调说明：服务端、手机端、眼镜端三端如何启动与观察。

交付物：

1. Phase I 测试集。
2. 手机接入联调说明。

完成定义（DoD）：

1. 本地模拟联调可稳定通过。
2. 三端联调日志能清晰展示注册、绑定、在线状态变化。

---

## 5.2 Phase J：眼镜-手机直连视频任务

### J1. `peer_link` 协议与直连准备

任务：

1. 明确 `peer_link.prepare / peer_link.ready / peer_link.failed / peer_link.close` 的最小控制语义。
2. 约定直连任务由服务端创建与协调，但媒体数据面走眼镜与手机之间的直连通道。
3. 明确网络协商最小方案，例如：
   - 同局域网直连优先
   - 首版允许使用服务端协调地址交换
4. 定义直连任务失败、超时、对端离线时的回收机制。

交付物：

1. `peer_link` 最小协议说明。
2. 服务端直连协调器。

完成定义（DoD）：

1. 服务端可为绑定的眼镜和手机发起一次直连准备。
2. 两端能明确回报“已准备好 / 准备失败”。
3. 失败路径可进入结构化任务事件与通知链路。

---

### J2. `phone_video_link_task` 最小闭环

任务：

1. 在 `backend-task-core` 中新增 `phone_video_link_task` 模板。
2. 任务负责：
   - 检查绑定关系
   - 协调直连准备
   - 下发眼镜视频流开始/停止指令
   - 维护任务运行态
3. 提供高层 Tool，例如：
   - `prepare_phone_video_link`
   - `start_phone_video_link`

交付物：

1. `phone_video_link_task`
2. 相关高层 Tool
3. 任务查询与取消能力

完成定义（DoD）：

1. Agent 可通过 Tool 创建一次眼镜-手机直连视频任务。
2. 任务可进入 `running`，并能被查询与取消。
3. 任务异常时可产出标准 `TaskEvent`。

---

### J3. 持续视频流数据面

任务：

1. 眼镜端实现 `/ws/camera + MediaFrame(camera_frame)` 持续上行能力。
2. 手机端实现相应的视频接收与解析能力。
3. 首版支持 JPEG 帧流即可，不提前追求复杂编解码优化。
4. 服务端仅负责控制与状态，不转发原始视频字节。

交付物：

1. 眼镜端视频流发送模块。
2. 手机端视频流接收模块。
3. `camera_frame` 数据面联调说明。

完成定义（DoD）：

1. 手机端页面可实时回显来自眼镜的视频帧。
2. 眼镜停止任务后，视频流能被及时关闭。
3. 相机抓拍链路与持续视频链路的资源竞争有明确策略。

---

### J4. 测试与联调

任务：

1. 单元测试：`peer_link` 状态推进、任务状态机、数据面帧编解码。
2. 集成测试：创建任务、视频启动、任务取消。
3. 真机联调：眼镜采集、手机显示、服务端观察。

交付物：

1. Phase J 测试集。
2. 直连视频联调说明。

完成定义（DoD）：

1. 第 10 项达到最小验收：模型可通过工具创建手机与眼镜直连后台任务。
2. 手机端测试页面可看到眼镜视频流。

## 5.3 Phase K：手机端视觉能力最小迁移

### K1. 手机端视觉执行框架

任务：

1. 在手机端建立本地任务中心最小骨架。
2. 建立视觉 Tool 抽象，屏蔽 YOLO 或后续模型实现细节。
3. 支持从视频帧输入得到结构化检测结果。
4. 支持把结果转换为：
   - 任务事件
   - 对眼镜的执行请求
   - 对服务端的状态上报

交付物：

1. 手机端本地任务中心骨架。
2. 手机端视觉 Tool 接口与检测结果模型。

完成定义（DoD）：

1. 手机端不再只是接流显示，而能对帧执行真实检测。
2. 检测结果不直接暴露底层模型细节，而是输出结构化语义。

---

### K2. 首个旧项目视觉能力迁移

任务：

1. 从旧项目中选择一个最适合作为首个迁移样板的能力。
2. 建议优先级：
   - `find_object` 优先
   - 其次 `traffic_light`
   - 再其次 `blindpath`
3. 将旧逻辑拆分为：
   - 手机端检测逻辑
   - 服务端任务模板
   - 眼镜端通知与执行策略

交付物：

1. 首个迁移完成的视觉任务模板。
2. 与旧项目逻辑对应关系说明。

完成定义（DoD）：

1. 至少 1 个旧项目视觉能力不再运行在服务端，而是在手机端完成检测。
2. 用户可通过语音触发该能力，并得到眼镜端语音反馈。
3. 服务端可以查询该任务当前状态与最近检测结果摘要。

---

### K3. 视觉结果与通知编排

任务：

1. 把手机端视觉结果接入 `backend-task-core -> TaskEvent -> NotificationCoordinator` 主路径。
2. 区分：
   - 普通状态变化
   - 高优先级安全提示
   - 任务完成提示
3. 明确哪些结果直发眼镜，哪些必须先回流 `agent-core`。

交付物：

1. 视觉任务事件桥接逻辑。
2. 对应通知策略说明。

完成定义（DoD）：

1. 手机端视觉任务不会绕过服务端私自播报。
2. 高优先级视觉告警可抢占当前低优先级播报。
3. 同一事件不会被手机端任务与 Agent 重复播报。

---

### K4. 测试与联调

任务：

1. 单元测试：视觉结果结构化、任务状态推进、通知去重。
2. 集成测试：视频帧输入 -> 手机检测 -> 服务端事件 -> 眼镜播报。
3. 真机联调：至少完成 1 个旧项目视觉能力迁移闭环。

交付物：

1. Phase K 测试集。
2. 视觉能力迁移联调说明。

完成定义（DoD）：

1. 旧项目首个视觉能力迁移在新架构下可真实跑通。
2. 第三阶段形成可复制迁移样板，后续能力可按同一模式继续迁入。

## 6. 依赖关系与推荐实施顺序

推荐严格按以下顺序推进：

1. 先做 Phase I  
原因：没有手机注册与绑定，后续所有跨端能力都无从谈起。

2. 再做 Phase J  
原因：没有直连视频任务和视频数据面，手机端无法承接视觉检测主链路。

3. 然后做 Phase K  
原因：只有在手机真正能收流并跑检测后，旧项目视觉迁移才有现实承载点。

4. 最后做 Phase L  
原因：导航执行期是多依赖汇合点，依赖地图真实接入、任务模板、手机视觉事件和通知协调。

不建议的顺序：

1. 直接先做 `navigation_task`
2. 直接先做全部 YOLO 迁移
3. 在手机未注册前就实现大量眼镜-手机业务逻辑

这些顺序会导致大量代码只能先写占位，后续返工成本高。

4. 手机页面可回显眼镜实时视频流。

范围：

3. 服务端可查询任务状态与最近事件。

通过标准：

范围：

## 8. 风险与注意事项

1. 最大风险是手机端工程长期停留在“模拟入口”，导致第三阶段无法真正起步。
2. 第二个风险是持续视频流协议迟迟不落，单次抓拍链路无法替代旧项目视觉主链路。
3. 第三个风险是把导航继续做成 `agent-core` 内部临时逻辑，绕开 `backend-task-core`，这会破坏现有架构边界。
4. 第四个风险是通知策略失控，手机视觉、导航任务和 Agent 同时抢播，最终用户体验会比旧项目更差。
5. 第五个风险是真机联调环境割裂，因此本阶段必须同步维护跨设备联调文档，而不是只保留服务端单测。
