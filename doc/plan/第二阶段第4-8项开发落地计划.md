# 第二阶段第 4-8 项开发落地计划

## 1. 文档目标与范围

本文档用于将第一期中的以下任务落地为可执行计划，覆盖：

1. `agent-core` 最小运行时落地。
2. `Skills / MCP` 最小能力层落地。
3. `backend-task-core` 最小闭环落地。
4. 拍照 Skill 与图片解读能力落地。
5. AMap MCP 导航能力落地。

本文档对应原始计划中的：

1. 第 4 项：AgentCore 调工具。
2. 第 5 项：Skills 与 MCP。
3. 第 6 项：拍照 Skill + 图片解读。
4. 第 7 项：AMap MCP 导航。
5. 第 8 项：后台任务管理 Skill。

本文档不覆盖：

1. 实时语音打断能力重构。
2. 手机端 YOLO 迁移与眼镜手机直连视频链路全量落地。
3. 导航最终执行期的手机视觉协同能力。

---

## 2. 阶段规划

| 阶段 | 阶段目标 | 里程碑 |
| --- | --- | --- |
| Phase D | `agent-core` 最小运行时可接入现有 `voice-runtime` | 一轮语音转写文本可进入 Agent Loop，并完成直接回复或调用 Tool |
| Phase E | 能力层骨架落地，打通 Tool / Skill / MCP | 至少打通 `capture_photo`、`query_task_status`、`amap` mock/adapter |
| Phase F | `backend-task-core` 最小闭环落地 | `timer_task` 可完成创建、查询、取消、完成通知 |
| Phase G | 拍照 Skill + 图片解读闭环落地 | 模型可自主触发抓拍并基于图片返回语音答复 |
| Phase H | AMap 导航准备与导航任务闭环落地 | 模型可完成目的地澄清、路线确认、导航任务创建与状态查询 |

---

## 3. 总体实施原则

1. `voice-runtime` 继续只负责语音输入输出边界，不回退到“大一统编排器”。
2. `agent-core` 先承接开放式决策，不提前吞掉 `backend-task-core` 的生命周期管理。
3. `Skill` 短期按当前设计结论，先实现为“业务型高级 Tool”，不单独建设复杂 Skill Runtime。
4. `MCP` 先通过统一 gateway / adapter 接入，不让业务代码直接耦合底层 SDK。
5. `Task` 必须从第一版开始进入标准注册、状态机、事件流，不允许临时线程或临时协程偷跑。
6. 每个阶段都要有“单元测试 + 集成测试 + 三端联调方案”三类验收证据。

## 4. 工作分解（WBS）

## 4.1 Phase D：`agent-core` 最小运行时

### D1. Agent 接入边界

任务：

1. 定义 `voice-runtime -> agent-core` 的输入对象，例如 `AgentTurn`。
2. 定义 `agent-core -> voice-runtime` 的输出对象，例如：
   - 最终回复
   - 追问
   - 能力调用结果
3. 明确当前 `VoiceSessionController` 只负责：
   - ASR
   - turn 提交
   - 播放控制

交付物：

1. `AgentFacade`
2. `AgentSession / AgentTurn / DialogState` 最小对象模型
3. `voice-runtime` 到 `agent-core` 的接入层

完成定义（DoD）：

1. ASR 文本不再直接在 `voice-runtime` 内部调用大模型。
2. 一轮用户语音可以进入 `agent-core` 并得到统一结果对象。

---

### D2. Agent Loop 最小实现

任务：

1. 基于 OpenAI Agents SDK 落地最小 `Runner` 封装。
2. 接入短期会话上下文。
3. 支持三类动作：
   - `final_answer`
   - `ask_user`
   - `call_tool`
4. 落地统一错误包装与失败回传。

交付物：

1. `agent-core` 主运行入口
2. 最小上下文装配器
3. 决策结果模型与错误模型

完成定义（DoD）：

1. Agent 可以基于历史上下文直接回答。
2. Agent 可以触发至少一个 Tool。
3. Tool 失败时可回到对话链路，生成明确错误回复。

---

### D3. 上下文与资产引用

任务：

1. 落地 `MessageContext / MediaAssetRef / DerivedArtifact / CapabilityTrace / TaskRef` 最小存储结构。
2. 把当前语音输入、ASR 结果、模型回复统一写入会话上下文。
3. 为后续图片、任务事件回流预留引用能力。

交付物：

1. 会话上下文存储模块
2. 资产引用与派生结果存储结构

完成定义（DoD）：

1. 一轮语音对话的输入、输出、转写结果都可结构化查询。
2. 后续图片输入和任务事件可以无侵入接入同一上下文模型。

---

### D4. 测试与联调

任务：

1. 单元测试：上下文装配、Agent 输出解析、错误包装。
2. 集成测试：`voice-runtime -> agent-core -> voice-runtime` 最小闭环。
3. 联调说明：如何观察 turn 输入、工具调用和最终回复。

交付物：

1. `agent-core` 首批测试
2. Phase D 联调说明

完成定义（DoD）：

1. 一轮真实或模拟语音对话可通过 `agent-core` 完成回复。
2. 关键日志可追踪 `session_id / turn_id / capability_trace`。

---

## 4.2 Phase E：Tool / Skill / MCP 能力层骨架

### E1. Tool Registry 与 Tool Gateway

任务：

1. 建立统一 Tool 注册表。
2. 定义 Tool schema、调用入口、错误包装规则。
3. 首批落地 Tool：
   - `query_device_state`
   - `capture_photo`
   - `create_timer`
   - `query_task_status`
   - `cancel_task`

交付物：

1. `ToolRegistry`
2. `ToolGateway`
3. 首批 Tool 实现

完成定义（DoD）：

1. Agent 可稳定发现并调用首批 Tool。
2. Tool 输入输出 schema 固定，异常路径统一。

---

### E2. Skill Registry 最小实现

任务：

1. 按“业务型高级 Tool”方式实现 Skill 注册。
2. 建立 `skill.call/result/failed` 的内部对象模型。
3. 首批 Skill：
   - `photo_interpret`
   - `timer_manage`

交付物：

1. `SkillRegistry`
2. `SkillGateway`
3. 首批 Skill 包装实现

完成定义（DoD）：

1. Agent 可以像调用 Tool 一样调用 Skill。
2. Skill 内部允许组合 Tool / MCP / TaskGateway。

---

### E3. MCP Gateway 与 AMap Adapter

任务：

1. 建立统一 MCP adapter 层。
2. 屏蔽底层 SDK / 协议细节。
3. 首批实现 AMap 相关原子接口：
   - `amap.poi_search`
   - `amap.geocode`
   - `amap.route_plan`

交付物：

1. `McpGateway`
2. `AmapMcpAdapter`
3. mock / stub 与真实接入配置规范

完成定义（DoD）：

1. Agent 或 Skill 可通过统一网关调用 AMap。
2. 超时、错误码、参数转换不暴露给上层业务。

---

### E4. 测试与联调

任务：

1. 单元测试：registry、schema、gateway、adapter。
2. 集成测试：Agent 触发 Tool、Skill、MCP。
3. 联调说明：如何替换 mock / 真实 AMap 环境。

交付物：

1. Phase E 测试集
2. 能力层联调说明

完成定义（DoD）：

1. 至少 1 个 Tool、1 个 Skill、1 个 MCP 能在一轮 AgentTurn 中串起来。
2. 调用轨迹可被 `CapabilityTrace` 记录。

---

## 4.3 Phase F：`backend-task-core` 最小闭环

### F1. Task Runtime 骨架

任务：

1. 落地 `TaskRegistry / TaskManager / TaskContextStore / TaskEventBus / TaskStateMachine / TaskGateway`。
2. 固定 `TaskSpec / TaskRuntime / TaskCommand / TaskEvent` 结构。
3. 实现统一状态机：
   - `created`
   - `scheduled`
   - `running`
   - `waiting_external`
   - `completed`
   - `cancelled`
   - `failed`
   - `timeout`

交付物：

1. `backend-task-core` 核心骨架
2. 标准状态迁移规则

完成定义（DoD）：

1. 不同任务模板可以按统一方式注册和实例化。
2. 任务状态迁移有统一校验，不允许模板各自乱定义。

---

### F2. `timer_task` 最小闭环

任务：

1. 实现 `timer_task` 模板。
2. 支持：
   - 创建
   - 查询
   - 取消
   - 完成事件
3. 任务完成后产出标准 `task.completed` 事件。

交付物：

1. `timer_task`
2. `create_timer / query_task_status / cancel_task` 与 `TaskGateway` 对接

完成定义（DoD）：

1. 用户说“帮我计时三分钟”可创建任务。
2. 用户说“还有多久”可查询任务。
3. 用户说“取消计时”可取消任务。
4. 计时结束后可触发事件并回流对话链路。

---

### F3. 任务事件回流 AgentTurn

任务：

1. 把 `TaskEventBus` 事件桥接到 `agent-core`。
2. 建立事件优先级策略：
   - `low`
   - `normal`
   - `high`
   - `critical`
3. 首版默认：
   - 正常事件先回流 `agent-core`
   - 高优先级事件允许直达设备，同时回流上下文

交付物：

1. 任务事件桥接器
2. 通知策略最小实现

完成定义（DoD）：

1. `timer_task` 完成后，Agent 能结合上下文决定如何播报。
2. 任务事件会进入会话上下文，而不是丢失在后台线程里。

---

### F4. 测试与联调

任务：

1. 单元测试：状态迁移、事件发布、任务查询。
2. 集成测试：Agent 创建任务到任务完成通知闭环。
3. 联调说明：如何模拟长任务、查询、取消、完成通知。

交付物：

1. Phase F 测试集
2. `timer_task` 联调说明

完成定义（DoD）：

1. `timer_task` 成为后续后台任务模板的基线样板。
2. 第 8 项达到“最小闭环验收”。

---

## 4.4 Phase G：拍照 Skill + 图片解读

### G1. 相机控制与图片资产链路

任务：

1. 补控制消息：
   - `sensor.camera.capture`
   - `sensor.camera.captured`
2. 眼镜端实现抓拍一张图并回传。
3. 服务端实现图片资产落盘与 `MediaAssetRef` 记录。

交付物：

1. 抓拍控制面
2. 图片回传链路
3. 图片资产存储

完成定义（DoD）：

1. 服务端可对指定设备发抓拍请求并收到图片。
2. 图片可进入统一上下文与资产引用系统。

---

### G2. `photo_interpret` Skill

任务：

1. 把 `capture_photo` Tool 与图片解读模型调用封装成 `photo_interpret` Skill。
2. Skill 输出结构化结果与用户可读摘要。
3. Agent 能自主决定：
   - 是否先抓拍
   - 是否基于图片回答
   - 是否继续追问

交付物：

1. `photo_interpret` Skill 实现
2. 图片解读提示词与结果包装

完成定义（DoD）：

1. 用户说“帮我看一下前面有什么”，Agent 可自主调用抓拍与图片解读。
2. 回复进入当前语音播报链路，不需要人工指定调用步骤。

---

### G3. 测试与联调

任务：

1. 单元测试：图片资产存储、Skill 输出解析。
2. 集成测试：语音输入 -> Agent -> 抓拍 -> 图片解读 -> 播报。
3. 真机联调方案：眼镜抓拍、服务器资产落盘、语音播报结果。

交付物：

1. Phase G 测试集
2. 抓拍解读联调说明

完成定义（DoD）：

1. 第 6 项达到完整闭环。
2. 相机链路为后续导航和视觉任务复用打下基础。

---

## 4.5 Phase H：AMap 导航准备与导航任务

### H1. 导航准备 Skill

任务：

1. 实现 `prepare_navigation` Skill。
2. 能完成：
   - 目的地候选查找
   - 歧义消解
   - 出行方式确认
   - 路线偏好确认
3. 把结构化导航参数产出为任务输入。

交付物：

1. `prepare_navigation` Skill
2. 导航参数对象模型

完成定义（DoD）：

1. 用户说“导航去桂林路地铁站”，Agent 不会直接盲目开任务。
2. Agent 会先澄清参数并形成结构化导航输入。

---

### H2. `navigation_task` 最小闭环

任务：

1. 基于 `backend-task-core` 实现 `navigation_task` 模板。
2. 首版重点放在：
   - 任务创建
   - 路线信息保存
   - 导航状态查询
   - 关键导航事件上报
3. 先不把手机视觉协同全部做进来。

交付物：

1. `navigation_task`
2. 任务状态与导航事件模型

完成定义（DoD）：

1. Agent 可基于用户确认结果创建导航任务。
2. 用户可查询当前导航状态。
3. 导航任务具备后续接入手机视觉与最后 10 米引导的扩展位。

---

### H3. AMap MCP 深化接入

任务：

1. 把 `poi_search / geocode / route_plan` 真正接入导航 Skill / Task。
2. 统一路线摘要生成与错误包装。
3. 建立 AMap 调用失败时的回退策略。

交付物：

1. AMap 导航能力闭环
2. 统一路线摘要与异常策略

完成定义（DoD）：

1. 第 7 项达到“可确认、可创建、可查询”的最小导航闭环。
2. 后续只需继续接入执行期能力，不需要推翻架构。

---

### H4. 测试与联调

任务：

1. 单元测试：导航参数组装、MCP adapter、任务状态。
2. 集成测试：用户请求 -> 澄清 -> 路线确认 -> 创建导航任务。
3. 联调说明：真实 AMap 配置、错误排查、任务观察接口。

交付物：

1. Phase H 测试集
2. 导航联调说明

完成定义（DoD）：

1. 第 7 项达到可演示、可回归测试状态。
2. 导航任务成为后续跨端执行期能力的主承载体。

## 5. 阶段依赖关系

建议严格按下面顺序推进：

1. `Phase D`
2. `Phase E`
3. `Phase F`
4. `Phase G`
5. `Phase H`

原因：

1. 没有 `agent-core`，第 4-8 项没有统一决策入口。
2. 没有 Tool / Skill / MCP gateway，第 6、7、8 项会各自重写一套调用逻辑。
3. 没有 `backend-task-core`，计时器和导航都只能写成临时协程，后面一定返工。
4. `photo_interpret` 比导航简单，适合作为第一个“业务型高级 Tool / Skill”样板。
5. `navigation_task` 依赖最重，应该最后做。

## 6. 每阶段建议验收口径

### Phase D 验收

1. 一轮语音输入进入 `agent-core`。
2. Agent 可直接回答或调用 Tool。
3. `voice-runtime` 只保留 I/O 边界职责。

### Phase E 验收

1. 首批 Tool / Skill / MCP 都能被 Agent 发现和调用。
2. 所有能力调用有统一 trace 和错误包装。

### Phase F 验收

1. `timer_task` 可创建、查询、取消、完成通知。
2. 任务事件可回流 AgentTurn。

### Phase G 验收

1. 模型可自主触发拍照。
2. 图片可进入资产存储。
3. 基于图片的答复可完成语音播报。

### Phase H 验收

1. 模型可完成导航参数澄清。
2. 可创建导航任务。
3. 可查询导航状态。
4. AMap 调用与任务状态进入统一上下文。

## 7. 风险与控制点

1. 最大风险不是 SDK 接入，而是边界回退。必须防止 `voice-runtime`、`agent-core`、`task-core` 重新互相侵入。
2. 第二大风险是“Skill 先做复杂”。当前阶段必须坚持 `Skill = 业务型高级 Tool`。
3. 第三大风险是导航过早进入执行细节。首版导航任务只做“准备和控制面”，不要立即吞掉手机视觉协同。
4. 第四大风险是测试环境漂移。后续阶段的测试和脚本建议统一到 `uv + Python>=3.11`，不要继续依赖裸 `python3`。
