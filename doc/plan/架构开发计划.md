# 架构开发计划

## 1. 文档目标

本文仅关注架构开发工作，不包含具体功能闭环实现细节。目标是为第一阶段提供稳定、统一、可扩展的系统底座，使后续功能开发可以在统一约束下推进。

本文回答的问题是：

- 三端架构底座需要先建设哪些能力。
- 各模块的职责边界如何划分。
- 架构开发应按什么顺序推进。
- 架构工作完成后，如何判断其已经具备支撑功能开发的条件。

## 2. 架构开发范围

第一阶段架构开发只包含以下内容：

- 统一协议模型
- 统一数据模型
- 三端工程骨架
- 连接管理与设备注册
- Agent 运行时框架
- Skill 接口框架
- MCP 接入框架
- 后台任务运行时框架
- 日志、追踪、配置、错误处理基础设施
- 基础测试与联调支撑工具

以下内容不属于架构开发范围：

- 非实时语音问答业务闭环
- 实时语音打断业务闭环
- 拍照图片解读功能闭环
- 计时器业务逻辑
- 导航业务逻辑
- 手机视频流业务任务逻辑

这些内容统一归入功能开发计划。

## 3. 架构设计原则

### 3.1 分层原则

- `protocol` 层负责协议、数据结构、序列化约束。
- `api` 层负责设备接入、连接管理、消息分发。
- `core` 层负责运行时、任务调度、状态机、生命周期管理。
- `skill` 层负责原子能力封装。
- `task` 层负责流程模板，但架构阶段仅提供任务运行框架，不实现具体业务流程。
- `infra` 层负责日志、配置、存储、通用基础能力。

### 3.2 跨端统一原则

- `Command`、`Event`、`State`、`Stream` 是三端统一概念。
- 所有跨端消息必须具备唯一标识、时间戳、来源、目标、追踪 ID。
- 所有任务实例必须统一生命周期状态。

### 3.3 可替换原则

- 大模型供应商、MCP 服务、Skill 实现都必须通过适配层接入。
- 不允许在核心运行时中硬编码外部服务调用细节。

### 3.4 可观测原则

- 关键连接事件必须有日志。
- 任务创建、状态变化、结束必须可追踪。
- 所有跨端请求必须能串联完整链路。

## 4. 三端模块落地边界

## 4.1 服务器侧

### `server-api`

职责：

- 设备接入
- 注册鉴权
- 长连接管理
- 消息路由
- 连接状态维护

不负责：

- 大模型对话编排
- 任务业务流程

### `agent-core`

职责：

- 管理大模型运行时
- 管理上下文
- 提供 Tool / Skill 调用能力
- 提供与后台任务中心的交互接口

不负责：

- 直接处理设备连接细节
- 直接实现具体 Skill 逻辑

### `backend-task-core`

职责：

- 管理后台任务生命周期
- 管理任务注册表
- 管理任务状态与事件
- 负责异步任务调度框架

不负责：

- 具体业务任务细节

### `skill`

职责：

- 定义统一 Skill 接口
- 屏蔽底层能力实现差异

### `mcp`

职责：

- 统一外部服务适配方式
- 将外部响应转换成内部结构化结果

## 4.2 眼镜侧

### `glass-api`

职责：

- 与服务器建立连接
- 接收命令
- 上报事件
- 上报流式数据

### `sensor-hub`

职责：

- 管理摄像头、麦克风等采集器
- 进行采集调度与资源协调

### `actuator-hub`

职责：

- 管理播放、插播、震动等执行动作
- 管理优先级与打断策略

## 4.3 手机侧

### `phone-api`

职责：

- 与服务器接入通信
- 承接任务下发
- 上报任务状态与本地事件

### 本地 `backend-task-core`

职责：

- 承接本地长生命周期任务
- 作为本地图像处理与边缘计算运行时容器

## 5. 架构开发拆解

## 5.1 协议与数据模型

目标：建立三端共享语言。

任务：

- 定义设备模型
- 定义连接模型
- 定义消息头与消息体基础结构
- 定义 `Command`、`Event`、`State`、`Stream`
- 定义任务模型与状态机
- 定义媒体载荷结构
- 定义错误码和错误模型

交付物：

- 协议定义文档
- 数据结构定义代码
- 示例消息样本

验收标准：

- 三端对相同消息有统一解释
- 新增消息类型无需推翻既有协议

## 5.2 工程骨架与目录规范

目标：建立稳定代码组织方式。

任务：

- 规划 `server/src`、`phone/src`、`glass/src`
- 统一模块命名
- 建立测试目录规范
- 建立文档目录规范
- 建立配置与环境变量管理方式

交付物：

- 三端目录骨架
- 开发规范说明

验收标准：

- 团队成员可以快速判断新代码放置位置

## 5.3 接入层与设备管理

目标：完成服务器、眼镜、手机的统一接入底座。

任务：

- 实现设备注册
- 实现设备鉴权
- 实现心跳保活
- 实现断线重连
- 实现在线状态维护
- 实现消息路由与投递

交付物：

- 设备注册中心
- 长连接管理组件
- 在线设备状态表

验收标准：

- 服务器可识别已注册设备、在线状态和连接状态

## 5.4 Agent 运行时框架

目标：建立大模型驱动的统一中枢。

任务：

- 调研 AgentCore 或备选方案
- 定义 Agent 抽象接口
- 定义模型适配器接口
- 定义上下文管理容器
- 定义 Tool / Skill 调用注册机制
- 预留记忆与上下文压缩接口

交付物：

- Agent 运行时接口
- 模型适配层
- Tool / Skill 注册框架

验收标准：

- Agent 能在统一框架下接入不同模型和工具

## 5.5 Skill / MCP 统一接入框架

目标：建立通用能力接入标准。

任务：

- 定义 Skill 元数据结构
- 定义 Skill 输入输出规范
- 定义同步 / 异步执行模式
- 定义 MCP 适配器接口
- 建立 Skill 注册表
- 建立 MCP 注册表

交付物：

- Skill 基类
- MCP 基类
- 注册机制

验收标准：

- 任意新增 Skill / MCP 都可按统一方式注册和调用

## 5.6 后台任务运行时框架

目标：建立长生命周期任务执行底座。

任务：

- 定义任务实例模型
- 定义生命周期状态机
- 定义任务上下文
- 定义任务事件总线
- 定义创建、查询、取消、结束接口
- 设计任务完成回调与通知机制

交付物：

- 任务运行时框架
- 任务状态机
- 任务管理器

验收标准：

- 能托管多个后台任务实例且状态可查询

## 5.7 日志、追踪与基础测试

目标：提高联调效率，降低排障成本。

任务：

- 统一日志格式
- 引入 trace_id / message_id / task_id
- 记录关键连接事件
- 记录关键任务事件
- 建立协议层测试
- 建立状态机测试
- 建立基础联调 mock

交付物：

- 日志规范
- 基础测试用例
- 联调 mock 工具

验收标准：

- 一次任务的核心链路可以从日志中追出

## 7. 架构开发阶段计划

## 阶段 A0：技术预研与方案冻结

任务：

- 冻结通信方案
- 冻结语音模型接入方案
- 冻结 Agent 运行时选型
- 冻结手机直连方案
- 冻结 MCP 接入方式

退出标准：

- 关键外部依赖均已明确

## 阶段 A1：协议层与工程骨架

任务：

- 完成统一协议定义
- 完成统一数据模型
- 完成三端目录初始化
- 完成配置、日志、错误码基础设施

退出标准：

- 后续功能开发可在统一骨架上进行

## 阶段 A2：设备接入底座

任务：

- 完成眼镜接入底座
- 完成手机接入底座
- 完成设备注册与在线管理
- 完成消息路由

退出标准：

- 三端能以统一协议通信

## 阶段 A3：运行时底座

任务：

- 完成 Agent 运行时框架
- 完成 Skill / MCP 注册框架
- 完成后台任务运行时框架

退出标准：

- 功能开发不再需要绕过框架直接实现主流程

## 阶段 A4：可观测与测试底座

任务：

- 完成基础日志与追踪
- 完成关键状态机测试
- 完成联调 mock 工具

退出标准：

- 架构具备可调试、可测试能力

## 8. 架构开发交付清单

- 协议文档
- 数据模型定义
- 三端工程骨架
- 设备接入框架
- Agent 运行时框架
- Skill / MCP 接入框架
- 后台任务运行时框架
- 日志与追踪规范
- 测试骨架与联调工具

## 9. 架构验收标准

- 模块边界清晰
- 三端协议统一
- 核心运行时可复用
- 功能开发可以在不破坏架构的前提下进行
- 关键链路具备最小测试和日志能力

## 10. 下一步建议

架构计划完成后，建议优先输出两类配套文档：

1. 《统一协议与数据模型设计》
2. 《三端工程目录与模块骨架设计》

两者完成后，再进入第一批功能闭环开发。
