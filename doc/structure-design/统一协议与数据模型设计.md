# 统一协议与数据模型设计

## 1. 文档目标

本文定义第一阶段三端统一使用的协议模型与数据模型，作为 `server`、`glass`、`phone` 三端实现的共同约束。

本文解决以下问题：

- 三端之间交换什么类型的消息。
- 每类消息的统一包结构是什么。
- 设备、连接、任务、媒体、错误等核心对象如何建模。
- 哪些字段必须统一，哪些字段可以按端扩展。
- 协议设计如何支撑后续 Skill、Task、Agent、MCP 扩展。

本文定位为架构层协议文档，不绑定具体传输实现，但默认面向长连接通信与流式数据场景设计。

## 2. 设计原则

### 2.1 三端统一

- 服务器、眼镜、手机必须共享同一套核心消息类型。
- 相同语义不能因设备不同而定义不同字段名。

### 2.2 结构稳定

- 协议应优先保证可扩展，而不是一开始追求极致精简。
- 新增字段应尽量向后兼容。

### 2.3 消息可追踪

- 所有跨端消息必须具备唯一消息 ID。
- 同一业务链路内消息必须带有统一追踪 ID。

### 2.4 任务中心化

- 长生命周期行为统一建模为 Task。
- 即便只是一次短操作，也应尽量保留与任务模型兼容的扩展方式。

### 2.5 流与控制分离

- 控制类消息与流式媒体消息使用统一包头，但语义分层明确。
- 音频、图片、视频、IMU 等持续数据统一归类为 `Stream`。

## 3. 协议总体分层

统一协议分为四层概念：

1. 包络层 `Envelope`
2. 语义层 `Command / Event / State / Stream`
3. 领域对象层 `Device / Session / Task / Media / Error`
4. 业务载荷层 `Payload`

说明：

- 包络层解决“这条消息是谁发的、发给谁、属于哪条链路”。
- 语义层解决“这条消息在表达什么类型的意图”。
- 领域对象层解决“系统中的核心实体如何统一表示”。
- 业务载荷层解决“具体功能需要传哪些参数”。

## 4. 核心对象模型

## 4.1 Device 设备模型

设备是系统中的一等实体，服务器、眼镜、手机都必须以统一设备模型标识。

建议字段：

| 字段                 | 类型         | 必填 | 说明                               |
| -------------------- | ------------ | ---- | ---------------------------------- |
| `device_id`        | `string`   | 是   | 设备唯一 ID                        |
| `device_type`      | `string`   | 是   | `server` / `glass` / `phone` |
| `device_name`      | `string`   | 否   | 设备显示名                         |
| `device_model`     | `string`   | 否   | 设备型号                           |
| `firmware_version` | `string`   | 否   | 固件或应用版本                     |
| `protocol_version` | `string`   | 是   | 协议版本                           |
| `capabilities`     | `string[]` | 是   | 设备能力列表                       |
| `status`           | `string`   | 是   | 在线状态                           |
| `last_seen_at`     | `string`   | 否   | 最近心跳时间，ISO8601              |
| `metadata`         | `object`   | 否   | 扩展字段                           |

建议枚举：

- `device_type`:

  - `server`
  - `glass`
  - `phone`
- `status`:

  - `offline`
  - `registering`
  - `online`
  - `busy`
  - `sleeping`
  - `error`

能力 `capabilities` 示例：

- `audio_input`
- `audio_output`
- `camera_capture`
- `video_stream_push`
- `imu_stream_push`
- `vibration_output`
- `local_yolo`
- `gps`
- `asr`

用于描述眼镜与手机的一对一绑定关系。

建议字段：

| 字段                | 类型       | 必填 | 说明        |
| ------------------- | ---------- | ---- | ----------- |

| `updated_at`      | `string` | 是   | 更新时间    |
| `metadata`        | `object` | 否   | 扩展字段    |

建议枚举：

- `status`:
  - `pending`
  - `active`
  - `broken`
  - `revoked`

## 4.3 Session 会话模型

Session 用于描述一段逻辑连接上下文，不等同于长连接本身。

建议分三类：

- `pairing_session`
- `conversation_session`
- `task_session`

建议字段：

| 字段             | 类型         | 必填 | 说明           |
| ---------------- | ------------ | ---- | -------------- |
| `session_id`   | `string`   | 是   | 会话 ID        |
| `session_type` | `string`   | 是   | 会话类型       |
| `participants` | `string[]` | 是   | 参与设备或组件 |
| `status`       | `string`   | 是   | 会话状态       |
| `started_at`   | `string`   | 是   | 开始时间       |
| `ended_at`     | `string`   | 否   | 结束时间       |
| `context`      | `object`   | 否   | 会话上下文     |

建议枚举：

- `status`:
  - `created`
  - `active`
  - `paused`
  - `ended`
  - `failed`

## 5. 统一消息包结构

所有跨端消息统一使用 `Envelope` 包装。

建议 JSON 结构：

```json
{
  "message_id": "msg_01",
  "trace_id": "trace_01",
  "correlation_id": "msg_00",
  "message_type": "command",
  "message_name": "audio.start_record",
  "protocol_version": "1.0.0",
  "source": {
    "device_id": "glass_001",
    "module": "glass-api"
  },
  "target": {
    "device_id": "server_main",
    "module": "server-api"
  },
  "task_id": "task_01",
  "session_id": "sess_01",
  "priority": "normal",
  "timestamp": "2026-04-07T21:00:00+08:00",
  "requires_ack": true,
  "payload": {
    "reason": "user_press_button"
  }
}
```

字段说明：

| 字段                 | 类型        | 必填 | 说明                                |
| -------------------- | ----------- | ---- | ----------------------------------- |
| `message_id`       | `string`  | 是   | 当前消息唯一 ID                     |
| `trace_id`         | `string`  | 是   | 同一链路追踪 ID                     |
| `correlation_id`   | `string`  | 否   | 关联上一条消息 ID，常用于响应或回执 |
| `message_type`     | `string`  | 是   | 语义分类                            |
| `message_name`     | `string`  | 是   | 具体消息名                          |
| `protocol_version` | `string`  | 是   | 协议版本                            |
| `source`           | `object`  | 是   | 来源                                |
| `target`           | `object`  | 是   | 目标                                |
| `task_id`          | `string`  | 否   | 关联任务                            |
| `session_id`       | `string`  | 否   | 关联会话                            |
| `priority`         | `string`  | 否   | 消息优先级                          |
| `timestamp`        | `string`  | 是   | 发送时间                            |
| `requires_ack`     | `boolean` | 否   | 是否要求确认                        |
| `payload`          | `object`  | 是   | 业务载荷                            |

`message_type` 建议枚举：

- `command`
- `event`
- `state`
- `stream`
- `ack`
- `error`

`priority` 建议枚举：

- `low`
- `normal`
- `high`
- `critical`

## 6. 语义层定义

## 6.1 Command

定义：请求对方执行一个动作。

特征：

- 通常具有明确目标。
- 可要求 ACK。
- 可与 Task 绑定。

建议命名规范：

- `<domain>.<action>`

示例：

- `audio.start_record`
- `audio.stop_record`
- `camera.capture`
- `peer.prepare_link`
- `peer.start_link`
- `peer.stop_link`
- `audio.play`
- `audio.stop`
- `task.start`
- `task.cancel`

Command 示例：

```json
{
  "message_type": "command",
  "message_name": "camera.capture",
  "payload": {
    "capture_mode": "single",
    "resolution": "1280x720",
    "return_mode": "upload"
  }
}
```

## 6.2 Event

定义：通知某个事实已经发生。

特征：

- 不要求对方执行动作。
- 更强调状态变化或客观事实。

示例：

- `audio.record_started`
- `audio.record_finished`
- `camera.capture_finished`
- `peer.link_established`
- `peer.link_broken`
- `task.completed`
- `task.failed`
- `user.speech_detected`

Event 示例：

```json
{
  "message_type": "event",
  "message_name": "task.completed",
  "payload": {
    "task_id": "task_01",
    "result_summary": "timer_finished"
  }
}
```

## 6.3 State

定义：某个对象的状态快照。

特征：

- 表达“当前是什么状态”，不是“刚刚发生了什么”。
- 适合周期上报或查询返回。

示例：

- `device.state`
- `connection.state`
- `task.state`
- `actuator.state`

State 示例：

```json
{
  "message_type": "state",
  "message_name": "task.state",
  "payload": {
    "task_id": "task_01",
    "status": "running",
    "progress": 0.4
  }
}
```

## 6.4 Stream

定义：连续分片的数据流。

特征：

- 高频、多片段。
- 可与 `media_id`、`chunk_index`、`frame_index` 结合使用。

示例：

- `audio.stream`
- `image.stream`
- `video.frame`
- `imu.stream`

Stream 示例：

```json
{
  "message_type": "stream",
  "message_name": "audio.stream",
  "payload": {
    "media": {
      "media_id": "media_01",
      "media_type": "audio_chunk",
      "codec": "pcm16",
      "sample_rate": 16000,
      "channels": 1,
      "chunk_index": 12,
      "is_final": false
    },
    "data": "base64-encoded-bytes"
  }
}
```

## 6.5 Ack

定义：对要求确认的消息进行接收确认或处理确认。

建议字段：

| 字段                 | 类型       | 必填 | 说明            |
| -------------------- | ---------- | ---- | --------------- |
| `acked_message_id` | `string` | 是   | 被确认的消息 ID |
| `ack_status`       | `string` | 是   | 确认状态        |
| `reason`           | `string` | 否   | 说明            |

建议枚举：

- `accepted`
- `rejected`
- `processed`

## 8. 状态机建议

## 8.1 设备连接状态机

建议状态：

- `offline`
- `connecting`
- `registering`
- `online`
- `degraded`
- `reconnecting`
- `error`

建议迁移：

- `offline -> connecting`
- `connecting -> registering`
- `registering -> online`
- `online -> degraded`
- `online -> reconnecting`
- `reconnecting -> online`
- 任意状态 -> `error`

## 8.2 任务状态机

建议状态：

- `created`
- `queued`
- `preparing`
- `running`
- `waiting_input`
- `paused`
- `completed`
- `cancelled`
- `failed`
- `timed_out`

建议迁移规则：

- `created -> queued`
- `queued -> preparing`
- `preparing -> running`
- `running -> waiting_input`
- `waiting_input -> running`
- `running -> paused`
- `paused -> running`
- `running -> completed`
- `running -> failed`
- `running -> cancelled`
- `running -> timed_out`

## 8.3 音频执行状态机

建议状态：

- `idle`
- `buffering`
- `playing`
- `interrupted`
- `completed`
- `failed`

## 9. 命名规范

### 9.1 消息名

统一使用：

- `<domain>.<action>`
- `<domain>.<state_name>`

示例：

- `system.register`
- `task.create`
- `audio.play`
- `camera.capture_finished`

### 9.2 ID 命名

建议前缀：

- `dev_`：设备 ID
- `sess_`：会话 ID
- `task_`：任务 ID
- `msg_`：消息 ID
- `trace_`：链路 ID
- `media_`：媒体 ID
- `link_`：直连链路 ID
- `skill_`：Skill 调用 ID

## 10. 兼容性与扩展约束

### 10.1 字段扩展规则

- 已发布字段不得随意改名。
- 新增字段优先放入可选字段。
- 端侧未知字段应忽略而不是报错。

### 10.2 版本规则

建议使用 `protocol_version` 表达协议版本。

第一阶段建议：

- 固定为 `1.0.0`
- 发生破坏性变更时再升级主版本

### 10.3 幂等规则

以下消息必须支持幂等处理：

- `system.register`
- `task.create`
- `task.cancel`
- `audio.stop`
- `peer.start_link`
- `peer.stop_link`

幂等依据：

- `message_id`
- 必要时结合 `correlation_id`
