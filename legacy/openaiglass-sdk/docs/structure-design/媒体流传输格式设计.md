# 媒体流传输格式设计

## 1. 目标

本设计回答第一期里最容易混淆的问题：

- 真实音频流和视频流是不是放在 `ControlMessage.payload` 里
- 真实媒体数据到底通过什么格式传
- 上行麦克风音频、下行播放音频、相机视频帧分别是什么二进制结构

结论先写清楚：

- 控制消息里不直接携带真实媒体字节
- 控制面只负责“建立什么流、什么时候开始、什么时候结束、这条流属于谁”
- 真实媒体数据走独立的数据面连接，使用二进制帧格式
- 但第一期回复下行是一个例外：为了兼容旧项目和降低设备侧改动，继续保留 `/stream.wav` 的 HTTP chunked 播放通道

## 2. 控制面与数据面的分工

### 2.1 控制面

承载：

- `device.register`
- `voice.session.open`
- `sensor.audio.segment.started`
- `sensor.audio.segment.finished`
- `actuator.audio.play`
- `actuator.audio.started`
- `actuator.audio.finished`

格式：

- 统一 `ControlMessage`
- JSON envelope

作用：

- 协商流参数
- 建立上下文
- 表达开始、结束、失败

### 2.2 数据面

承载：

- 麦克风音频块
- 回复播放音频块
- 相机视频帧

格式：

- 独立数据面连接
- 上行媒体优先使用 WebSocket 二进制消息
- 每条 WebSocket 二进制消息就是一个 `MediaFrame`
- 第一期开启回复播放时，继续允许使用 `/stream.wav` 的 HTTP chunked 音频流

作用：

- 低开销传输真实媒体字节

## 3. 第一阶段的物理通道

第一期建议保留三条物理通道：

1. 控制连接
   - 示例：`/ws/control`
   - 传 `ControlMessage`
2. 麦克风音频上行连接
   - 示例：`/ws_audio`
   - 传 `audio_chunk`
3. 播放音频下行连接
   - 示例：历史路径继续叫 `/stream.wav`
   - 首版继续使用 HTTP chunked 音频流
   - 里面传的是持续 PCM 音频块，不是整文件下载

如果后续接入相机持续视频流，再增加：

4. 相机视频流上行连接
   - 示例：`/ws/camera`
   - 传 `camera_frame`

## 4. 核心结论：媒体字节不放在 payload

例如这条控制消息：

```json
{
  "name": "actuator.audio.play",
  "stream_id": "stream_reply_01J...",
  "payload": {
    "mode": "stream",
    "format": "pcm16",
    "sample_rate": 16000,
    "channels": 1
  }
}
```

这里的 `payload` 只表达：

- 即将开始一条回复播放流
- 这条流的编码是什么
- 设备应该按什么参数去播放

它不直接承载真实音频字节。

真实音频字节要在独立的播放下行连接里连续发送。

## 5. 第一版统一二进制帧格式

下面这个 `MediaFrame` 结构适用于首版所有 WebSocket 数据面连接。

第一期播放下行 `/stream.wav` 不强制套这层头部，继续保持旧项目风格的 chunked 音频流。

第一期不需要自定义很重的二进制协议，建议统一采用下面这个简单结构：

```text
+----------------------+---------------------+------------------+
| 4 bytes header_len   | header_json bytes   | payload bytes    |
+----------------------+---------------------+------------------+
```

说明：

- `header_len`：无符号 32 位大端整数
- `header_json`：UTF-8 编码 JSON
- `payload`：真实媒体字节

这样设计的优点：

- Python、Node、ESP32 都容易实现
- 调试时能直接把 header JSON 打出来
- 不需要在第一期引入更复杂的 protobuf 或 RTP

## 6. MediaFrame 头部字段

建议 `header_json` 至少包含：

```json
{
  "version": "v1",
  "stream_id": "stream_01J...",
  "frame_type": "audio_chunk",
  "seq": 12,
  "ts_ms": 1744262400000,
  "codec": "pcm16le",
  "payload_size": 640,
  "final": false
}
```

字段说明：

- `version`
  - 当前固定为 `v1`
- `stream_id`
  - 对应控制面里建立的流上下文
- `frame_type`
  - 枚举：`audio_chunk`、`reply_audio_chunk`、`camera_frame`
- `seq`
  - 当前流内递增序号
- `ts_ms`
  - 发送时刻毫秒时间戳
- `codec`
  - 实际 payload 编码
- `payload_size`
  - 当前 payload 字节数
- `final`
  - 是否最后一帧

按需字段：

- `segment_id`
- `sample_rate`
- `channels`
- `width`
- `height`
- `frame_index`

## 7. 麦克风音频上行格式

## 7.1 连接时机

- 收到 `voice.session.open` 后建立 `/ws_audio`

## 7.2 控制面约定

`voice.session.open.payload` 只描述上行流参数，例如：

```json
{
  "sample_rate": 16000,
  "channels": 1,
  "codec": "pcm16",
  "endpoint": {
    "trailing_silence_ms": 800,
    "max_capture_ms": 10000
  }
}
```

## 7.3 数据面格式

每个 `audio_chunk` 的 `MediaFrame.header_json` 建议为：

```json
{
  "version": "v1",
  "stream_id": "stream_mic_01J...",
  "segment_id": "seg_01J...",
  "frame_type": "audio_chunk",
  "seq": 12,
  "ts_ms": 1744262400000,
  "codec": "pcm16le",
  "sample_rate": 16000,
  "channels": 1,
  "payload_size": 640,
  "final": false
}
```

`payload` 内容：

- 原始 `pcm16 little-endian`
- 单声道
- `16 kHz`

第一期建议：

- 每帧时长：`20ms`
- 每帧采样点：`320`
- 每帧字节数：`640`

注意：

- 只有在 `sensor.audio.segment.started` 之后，才允许发送当前 `segment_id` 的 `audio_chunk`
- `sensor.audio.segment.finished` 发出后，不再发送该 `segment_id` 的后续音频帧

## 8. 回复播放音频下行格式

## 8.1 连接时机

- 收到 `actuator.audio.play` 后建立播放下行连接

## 8.2 控制面约定

建议把控制消息写成：

```json
{
  "name": "actuator.audio.play",
  "stream_id": "stream_reply_01J...",
  "payload": {
    "mode": "stream",
    "format": "pcm16",
    "sample_rate": 16000,
    "channels": 1,
    "interrupt_policy": "forbid"
  }
}
```

这里建议把 `format` 明确写成 `pcm16`，而不是 `wav`。

原因：

- 流式播放时，设备真正需要的是连续 PCM 数据
- 如果模型返回的是 `wav`，服务端应先解码或去掉文件头，再按 PCM 块下发
- 即便历史路径名仍叫 `/stream.wav`，也不代表每个 chunk 都是完整 wav 文件

## 8.3 数据面格式

第一期回复下行冻结为：

- 物理承载：`/stream.wav`
- 传输方式：HTTP chunked
- 实际音频：连续 `pcm16le/16kHz/mono`

说明：

- 这里保留历史路径名 `/stream.wav`，只是为了兼容旧项目实现
- 实际下发的是连续 PCM 音频块，不要求每个 chunk 都是完整 wav 文件
- 第一版不强制要求每个下行 chunk 额外套 `MediaFrame.header_json`
- `stream_id`、格式、采样率等上下文通过 `actuator.audio.play` 控制消息给出

第一期建议：

- 服务端收到模型可播放音频后，转成 `pcm16le`
- 按 `20ms` 一块连续下发
- 设备收到首块可播放数据后立即开始播报

## 9. 相机视频流格式

第一期语音链路不依赖视频流，但拍照和后续相机流都建议使用同一套 `MediaFrame` 格式。

## 9.1 持续视频流

每个 `camera_frame` 的 `MediaFrame.header_json` 建议为：

```json
{
  "version": "v1",
  "stream_id": "stream_cam_01J...",
  "frame_type": "camera_frame",
  "seq": 42,
  "frame_index": 42,
  "ts_ms": 1744262400999,
  "codec": "jpeg",
  "width": 640,
  "height": 480,
  "payload_size": 18234,
  "final": false
}
```

`payload` 内容：

- 单帧 JPEG 二进制

建议策略：

- 新帧优先
- 网络拥塞时允许丢旧帧
- 第一阶段不做逐帧重传

## 9.2 单次抓拍

如果是 `sensor.camera.capture`：

- 控制面发 `sensor.camera.capture`
- 眼镜抓拍后返回 `sensor.camera.captured`
- 图片字节仍建议走同样的 `MediaFrame` 二进制结构

## 10. 错误处理

数据面错误不要靠 `payload` 里塞字符串表达，统一走控制面通知：

- 上行音频连接失败
  - `voice.session.closed` 或结构化错误消息
- 下行播放流失败
  - `actuator.audio.state`
- 视频流失败
  - `task.state.changed` 或对应相机错误消息

第一期最重要的不是细分所有错误码，而是做到：

- 控制面和数据面错误能明确区分
- 媒体字节不混进 JSON payload
- 每条数据帧都能通过 `stream_id` 找回所属会话

## 11. 第一版落地结论

第一期媒体流设计可以直接按下面落地：

1. 控制面继续使用统一 `ControlMessage`
2. 媒体字节不放进 `payload`
3. WebSocket 媒体消息采用 `4 bytes header_len + header_json + payload`
4. 麦克风上行使用 `pcm16le/16kHz/mono/20ms`
5. 回复下行继续沿用 `/stream.wav`，统一转成 `pcm16le/16kHz/mono/20ms`
6. 视频帧使用 `jpeg` 单帧二进制

做到这一步，协议已经足够支撑第一期真实实现。
