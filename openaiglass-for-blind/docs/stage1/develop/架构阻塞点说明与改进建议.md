# 架构阻塞点说明与改进建议

更新时间：2026-04-26

## 1. 当前业务开发结论

本轮基于 SDK 公开能力完成了 `traffic_light` 红绿灯识别业务能力的服务端、手机侧 Python 契约、离线场景回放和 iOS 插件样例。服务端 SDK 扩展面整体可用，未发现必须修改服务端 SDK 才能继续写业务 Tool/Task 的硬阻塞。

但推进到真实 iOS 手机端插件集成时，发现一个 SDK 产品化阻塞点：当前 iOS 通用运行时虽然有 `PhoneTaskCapabilityRuntime` 和 `PhoneCapabilityBootstrap`，但它不是一个可同时承载多个业务能力的注册表。

## 2. 阻塞点：iOS 手机能力运行时只能注册单个 Runtime

### 2.1 现象

SDK iOS 运行时当前通过：

```swift
PhoneCapabilityRuntimeFactory.register {
    SomeCapabilityRuntime()
}
```

注册手机能力运行时。`PhoneCapabilityRuntimeFactory` 内部只有一个 `builder`，后注册的业务能力会覆盖先注册的业务能力。

已有 `find_object` 插件和本轮新增的 `traffic_light` 插件都采用编译期 installer 模式。如果两个插件同时进入同一个 App target，最终只有最后一次 `register(...)` 生效。

### 2.2 影响

1. 无法在同一个 iOS 宿主里同时稳定承载 `find_object_phone_task` 和 `traffic_light_phone_task`。
2. 业务团队如果自行写组合 Runtime，会把多能力分发逻辑写到业务工程，后续每新增一个能力都要改组合器，等同于业务侧重复造 SDK 的能力注册表。
3. 这会影响第三阶段 Phase K 的目标：多个旧项目视觉能力迁移到手机端并可组合使用。

### 2.3 证据

相关代码：

1. `openaiglass-sdk/phone-ios/GlassesVideoReceiver/Core/CameraStreamStore.swift`
   - `PhoneCapabilityRuntimeFactory` 只保存单个 `builder`。
   - `PhoneCapabilityBootstrap` 只执行 installer，不提供按 `taskType` 分发的多能力注册表。
2. `openaiglass-for-blind/capabilities/find_object/phone/ios/FindObjectPhoneCapability.swift`
   - 使用 `PhoneCapabilityRuntimeFactory.register { FindObjectPhoneCapabilityRuntime() }`。
3. `openaiglass-for-blind/capabilities/traffic_light/phone/ios/TrafficLightPhoneCapability.swift`
   - 同样需要注册 `TrafficLightPhoneCapabilityRuntime()`。

## 3. 建议 SDK 团队改进方向

建议把 iOS 端能力扩展面从“单 Runtime builder”调整为“按任务类型注册的 Runtime Registry”：

1. 新增 `PhoneTaskCapabilityRegistry`。
2. 支持 `register(taskType: String, runtimeBuilder: ...)`。
3. `CameraStreamStore.startPhoneTask(...)` 按 `taskType` 选择对应能力运行时。
4. 允许多个手机任务并存时，按 `taskID` 管理实例生命周期。
5. 保留 `NoopPhoneTaskCapabilityRuntime` 作为未知任务类型的兜底。

建议接口示意：

```swift
PhoneTaskCapabilityRegistry.register(taskType: "find_object_phone_task") {
    FindObjectPhoneCapabilityRuntime()
}

PhoneTaskCapabilityRegistry.register(taskType: "traffic_light_phone_task") {
    TrafficLightPhoneCapabilityRuntime()
}
```

## 4. 次要改进建议：业务插件打包方式需要产品化

当前业务插件文件位于：

1. `capabilities/find_object/phone/ios/FindObjectPhoneCapability.swift`
2. `capabilities/traffic_light/phone/ios/TrafficLightPhoneCapability.swift`

但 SDK 文档还没有明确这些文件如何被稳定纳入 Xcode target、Swift Package 或 XCFramework。建议 SDK 团队补一个业务插件集成方式：

1. Swift Package plugin target。
2. 或 Xcode 工程中的业务能力 target group 约定。
3. 或 `openaiglass-for-blind/host/phone` 生成/装配 iOS App target 的脚本。

## 5. 当前业务侧处理方式

业务侧不修改 SDK：

1. Python 服务端能力已经完成并通过离线回放。
2. iOS 插件样例放在业务能力目录，供 SDK 团队接入多能力 registry 后验证。
3. 在 SDK 修复多能力注册表前，真机 iOS 同时启用多个视觉能力存在不稳定风险。
