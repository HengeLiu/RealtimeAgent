# 架构阻塞点说明与改进建议

更新时间：2026-04-28

本文只记录当前最新未疏通阻塞点。已经由 SDK 团队修复的 `glass-playback` 全双工实时语音握手问题不再保留。

## 1. 最新 SDK 阻塞点

### 1.1 glass-playback 保存播放音频会阻塞控制消息循环

2026-04-28 使用真实 `phone-001` 和 `glass-playback` 执行 `look_look.json` 数据回放时，链路已经能完成：

1. `device.registered`
2. `voice.realtime.session.opened`
3. `device.binding.ready`
4. `voice.trigger_audio.started`
5. `voice.trigger_audio.finished`
6. Agent 调用 `capture_photo`
7. 服务端下发 `sensor.camera.capture`

但当 `actuators.audio_play.save_audio_to` 打开时，`glass-playback` 在处理第一段 `actuator.audio.play` 时同步下载并保存 `/stream.wav`，控制消息循环被阻塞。随后服务端已经下发的 `sensor.camera.capture` 不能及时处理，导致业务 Tool 先超时，后续抓拍回传被服务端判定为未知请求：

```text
capture_photo TIMEOUT: 等待设备抓拍回传超时
收到未知抓拍回传，已忽略: request_id=...
```

当前业务回放配置已临时去掉 `save_audio_to`，让 `actuator.audio.play` 只做记录和自动完成，从而避免播放音频保存阻塞抓拍时序。

建议 SDK 团队处理：

1. `glass-playback` 的音频保存不应阻塞控制消息读取循环。
2. `actuator.audio.play` 的 `/stream.wav` 下载应放入后台线程，或者由独立队列异步保存。
3. 增加回归测试：服务端先发送 `actuator.audio.play`，随后发送 `sensor.camera.capture`，回放端必须在抓拍超时前返回 `sensor.camera.captured`。
4. 设备级验收脚本应提供“服务端业务产物已生成”的断言，而不只检查回放端事件日志。
