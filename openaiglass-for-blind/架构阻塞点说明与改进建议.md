# 架构阻塞点说明与改进建议

更新时间：2026-04-28

本文只记录当前基于 `sdk-v19` 做业务能力开发时遇到的最新未疏通阻塞点。旧版本已经解决或已经清理的内容不再保留，避免 SDK 团队误判当前优先级。

## 1. 当前结论

业务侧已按最新 SDK 边界完成一次收口：

1. 删除 `host/phone/src` 下手写 WebSocket 的 Python 手机调试入口。
2. 真实手机入口统一保留为 `host/phone/ios/GlassesVideoReceiver.xcodeproj`，通过 `uv run openaiglass.phone.open --app-root openaiglass-for-blind` 打开。
3. Python 虚拟手机统一使用 SDK 的 `openaiglass.phone.mock`，业务侧只保留 `host/phone-mock/config/phone.mock.json` 配置。
4. 服务端宿主不再给 `DeviceGroupRuntime` 手动注入视频链路 debug adapter。
5. 业务 Tool / Task 仍只通过 `BaseTool`、`BaseTask`、`TaskContext`、`DeviceGroupContext`、`context.mcp(...)` 等公开入口表达业务逻辑。

收口后，`timer` 和 `navigation` 这类不依赖眼镜到手机视频链路的能力仍可以继续作为业务层能力推进；`find_object` 和 `traffic_light` 的真实视频链路会暴露出 SDK 当前公开装配能力不足的问题，应由 SDK 团队补齐。

## 2. 最新 SDK 阻塞点

### 2.1 视频链路公开装配能力仍不完整

业务能力按指南调用：

```python
context.device_group.start_phone_video_link(...)
context.device_group.stop_phone_video_link(...)
```

但当前真实服务端运行时没有在 SDK 内部自动为 `DeviceGroupRuntime` 绑定 `video_link_start_adapter` 和 `video_link_stop_adapter`。如果业务宿主不手动注入 adapter，`find_object_task`、`traffic_light_task` 等依赖视频链路的能力会在启动阶段失败。

本次已经移除业务侧临时补丁，避免业务代码继续直接调用：

1. `ControlRuntime.start_phone_video_link_debug(...)`
2. `ControlRuntime.stop_phone_video_link_debug(...)`
3. `DeviceGroupRuntime.video_link_start_adapter`
4. `DeviceGroupRuntime.video_link_stop_adapter`

建议 SDK 团队处理：

1. 在 `build_server_handle_from_sdk(...)` 或 `ControlRuntime` 初始化阶段完成 `DeviceGroupRuntime` 视频链路 adapter 的标准绑定。
2. 明确 `start_phone_video_link(...)` 返回的 `phone_video_link_task` 快照结构，保证业务 Task 可通过 `context.device_group.query_task(link["task_id"])` 查询 `phase`、`stream_id`、`target_ws_uri`、错误信息等字段。
3. 将 `/api/debug/phone-video-link/start|stop` 与业务 `DeviceGroupContext.start_phone_video_link(...)` 收敛到同一套 SDK 系统任务入口，避免业务宿主依赖 debug 方法。
4. 在 SDK 预检中增加一项：真实 server handle 构建后，`DeviceGroupRuntime` 已具备视频链路启动和停止能力。

### 2.2 MCP Adapter 开发仍依赖 SDK 内部包路径

业务侧 `MockAmapMcpAdapter` 目前需要直接导入：

```python
from agent_core.mcp import BaseMcpAdapter
from agent_core.models import CapabilityResult, McpMethodSpec
```

这让业务能力依赖 SDK 内部 `agent_core` 包结构。虽然业务 Tool 调用 MCP 时已经通过公开的 `context.mcp(...)`，但业务开发一个 MCP adapter 时仍缺少稳定公开入口。

建议 SDK 团队处理：

1. 在 `openaiglasses` 公开导入入口中导出 `BaseMcpAdapter`、`McpMethodSpec` 和用于 MCP adapter 返回值的 `CapabilityResult`。
2. 在 SDK 指南中把 adapter 示例改成只从 `openaiglasses` 导入公开类型。
3. 在边界预检中允许业务导入 `openaiglasses` 公开 MCP 类型，同时继续禁止业务直接构造 `McpGateway`、`McpRegistry`、`AgentToolContext`。

### 2.3 Python 手机任务接口与 phone-mock 的边界仍需产品化

业务侧当前仍保留 Python `BasePhoneProcessor` / `BasePhoneTask` 实现，用于协议契约、mock 行为和本地能力验证；真实 iPhone 能力已经通过 Swift 插件接入 `PhoneTaskCapabilityRegistry.register(taskType:)`。

当前阻塞不在真实 iOS 插件，而在 Python phone mock 的产品化边界：

1. `phone-mock` 目前主要靠配置中的固定 mock 事件驱动。
2. 业务侧 Python `BasePhoneProcessor` / `BasePhoneTask` 还不能自然作为 `phone-mock` 的插件被独立设备进程加载。
3. 业务开发者容易误把 Python phone 代码理解为真实手机 App 插件。

建议 SDK 团队处理：

1. 为 `openaiglass.phone.mock` 增加业务 Python handler / processor 的加载机制，明确它只服务于 mock 和测试。
2. 在配置中声明 `task_type -> handler` 或 `processor_type -> processor` 的加载关系。
3. 在 SDK 文档中把 Python phone 接口标注为 `phone-mock` 扩展面，而不是 iOS 真机扩展面。
4. 增加 phone-mock 设备级断言和事件日志检查能力，减少业务侧再次创建组件级 ScenarioRunner 的冲动。

### 2.4 glass-playback 与全双工实时语音模式不兼容

2026-04-28 基于真实在线 `phone-001` 做临时数据回放 smoke 时，`glass-playback` 使用当前服务端已配置的 `glass-001` / `pair-demo-token` 成功完成：

1. `device.registered`
2. `device.binding.ready`
3. `voice.trigger_audio.started`
4. `voice.trigger_audio.finished`

但服务端当前配置为：

```text
VOICE_SESSION_MODE=full_duplex_realtime
```

真实日志显示服务端向回放眼镜发送的是 `voice.realtime.session.open`，不是半双工链路中的 `voice.session.open`。`glass-playback` 当前没有完成 `voice.realtime.session.opened` 一类的实时语音握手，也没有把实时会话 `session_id` 带入后续 `sensor.audio.segment.started`。服务端随后按协议关闭控制连接：

```text
控制消息处理失败，关闭当前控制连接: code=INVALID_MESSAGE
message=session_id 与当前语音会话不匹配
details={'expected_session_id': 'sess_741995a245cd', 'actual_session_id': ''}
```

这导致设备级数据回放在全双工模式下无法完成正式验收。业务侧不应修改 `glass-playback` 协议实现，也不应在业务测试脚本里伪造 SDK 会话状态。

建议 SDK 团队处理：

1. 为 `glass-playback` 补齐 `voice.realtime.session.open` / `voice.realtime.session.opened` 握手支持。
2. 在全双工模式下，保证回放端保存并复用服务端下发的 `session_id`，后续音频段控制消息必须携带正确 `session_id`。
3. 或者在 SDK CLI / preflight / live-check 中明确提示：当前 `glass-playback` 只支持 `VOICE_SESSION_MODE=half_duplex`，检测到 `full_duplex_realtime` 时应给出阻塞级诊断。
4. 将 `glass-playback` 的正式验收配置拆分为 `half_duplex` 与 `full_duplex_realtime` 两套，避免业务开发者在默认全双工配置下误以为数据资产或业务 Tool 出错。

## 3. 当前业务侧不再处理的内容

以下内容不再由 `openaiglass-for-blind` 业务侧补丁处理：

1. 不手写 `/ws/control`、`/ws/camera`、`/ws_audio` 或 `voice.realtime.*` 协议。
2. 不自行维护设备绑定表、在线表或视频链路状态机。
3. 不在业务宿主中直接调用 SDK debug 方法来补齐系统任务装配。
4. 不在能力目录保留 `scenario.py` 或组件级 ScenarioRunner。
5. 不把 Python phone 代码作为真实 iPhone 能力入口。

## 4. 后续观察风险

这些不是当前硬阻塞，但进入真实产品能力后需要继续观察：

1. 真实 AMap adapter 接入后，SDK MCP 错误包装是否足以表达配额、鉴权、超时、候选 POI 歧义和路线不可达。
2. `navigation_task` 进入更复杂手机视觉协同时，通知去重、抢播策略和多任务资源仲裁是否需要更明确的 SDK 公共能力。
3. `timer_task` 如果要求真实自然到点，SDK 是否需要提供通用定时事件调度能力。当前业务侧不私建线程。
4. 全双工实时语音真机验收时，端侧 AEC/VAD 和 `voice.realtime.user_interrupt` 的可观测字段是否足够排障。
